# roombapy-prime 0.4.0b1

**One library for iRobot's cloud, both robot generations.** ha_roomba_plus
has talked to iRobot's cloud through two clients: this library for Prime
robots, and its own `cloud_api.py` for the cloud side of Classic robots —
maps, mission history, part counters, favorites, automations. Two
implementations of the same signed API meant two places for every fix. This
release gives the Classic calls a home here, and gives both generations one
way in.

Controlling a Classic robot does not change. That stays local, over
roombapy. Only its cloud calls move.

## One account, every robot

Login, credentials and the session belong to the account; only the robots
differ. **`CloudAccount`** logs in once and hands out what each robot needs:

```python
account = await CloudAccount.login(session, username, password, "DE")
account.generation(blid)        # "prime", "classic", or None
account.rest(blid)              # ClassicRestClient or PrimeRestClient
await account.prime_robot(blid) # PrimeRobot, Prime only
```

An unknown SKU is `None`, and `rest()` refuses it rather than guess — the
SKU tables are incomplete for models nobody has tested.

Every REST client the account hands out relogs **through the account** on
HTTP 403. Clients that notice together share one login; a client whose
credentials were already replaced takes the new ones without logging in.
iRobot limits sessions per account, and `AuthRateLimitedError` is what two
logins where one would do brings closer.

There is deliberately no robot class for both generations: it would carry
methods that fail at runtime for one of them.

## Three REST classes

| Class | |
|---|---|
| `CloudRestClient` | The shared base: signing, request handling, relogin, and the calls both generations make the same way |
| `PrimeRestClient` | Prime robots, **unchanged**: same constructor, methods and import path |
| `ClassicRestClient` | **New.** `get_pmaps()`, `get_pmap_umf()`, `set_robot_part_counter()`, `get_mission_history()`, `get_favorites()`, `get_automations()` |

## Moved unchanged, and tested as unchanged

The Classic calls in ha_roomba_plus are confirmed on real robots, so the
tests pin that they did not change: the query (keys, values and order), the
body bytes and the SigV4 signature, compared with what ha_roomba_plus 4.2.12
sent. The Classic app's defaults are the client's defaults, so
`get_mission_history(blid)` alone is the request 4.2.12 sent.

What callers get back was compared too, against a local server answering
normally, oddly and wrongly. Where 4.2.12 returned something, this release
returns the same, with three exceptions:

- **A UMF answer without a map is an error**, empty body included. An empty
  object would be drawn as a blank map instead of reported unavailable.
- **`get_robot_parts_raw()` is raw**: it returns what the server sent, where
  4.2.12 turned anything but an object into `{}`.
- **An empty mission-history body is `{}`**, where 4.2.12 returned `None`.
  Neither is a list, so a caller checking for one sees no difference.

Where 4.2.12 **crashed** — a non-JSON body, a list where an object belonged,
an empty body — this release raises `RestError` or answers empty. Those
crashes were `ValueError`, `AttributeError` and `JSONDecodeError`, which
the integration's refresh did not catch.

And in the other direction: **ha_roomba_plus 4.2.12, unmodified, passes its
full test suite, `mypy --strict` and its attribute guards against this
release**, under Home Assistant 2025.5 and 2026.8.

## Every failure is a `CloudError`

**`CloudError`** sits above `AuthError`, `RestError`, `ShadowError` and
`SubscriptionRejectedError`. `except CloudError` now means "anything from
iRobot's cloud". Every class keeps its name and subclasses, and the three
families stay apart.

That promise needed fixing before it could be made. Measured against a local
server, a connection dropped mid-answer escaped as
`aiohttp.ServerDisconnectedError` and a timeout as a bare `TimeoutError`:
each login stage and each REST call caught three aiohttp errors and let the
rest through. A login answer missing a key it relied on — `httpBase`, the
Gigya api key, `UID` — or arriving as a list failed with a bare `KeyError`,
`TypeError` or `AttributeError`. All of these are mapped now, and every one
is tested; the same measurement repeated afterwards gives a `CloudError` in
each case.

An answer that is not a connection problem no longer reads like one: a
server error is a `RestError`, not "check your network".

## HTTP status says what to do

An error status was a plain `RestError` with the number in an attribute.
Three subclasses of the new **`RestHTTPError`** say it instead:

| | |
|---|---|
| `RestClientError` | 4xx — the request itself was refused. Sending it again unchanged will not help |
| `RestRateLimitedError` | 429 — later; `retry_after` carries the wait from the server's header |
| `RestServerError` | 5xx — on iRobot's side, usually temporary |

All three are `RestError`s, so nothing that catches `RestError` changes.

## Errors say why — in a form you can translate

The class says which part failed, not what to tell a person.
`AuthSSLError` alone covers a machine that cannot check certificates,
where waiting will not help, and an expired certificate on iRobot's side,
where it will. A Gigya lockout is an `AuthCredentialsError` so that Home
Assistant stops retrying — but a person told "credentials rejected"
re-enters the password, and each attempt extends the lockout. Only the
English message told these apart, and ha_roomba_plus passed that English
text into its German, French and Polish messages as it was.

Every `CloudError` now carries **`reason`**, one of 22 names in
`CloudErrorReason`:

```python
except CloudError as err:
    key = f"cloud_{err.reason}"     # "cloud_account_locked", "cloud_timeout", ...
```

The library does not translate; it states the cause, and the application
says it in its user's language. The English message stays, for logs. Data a
translation needs is an attribute, never part of the message: `status` on
REST errors, `retry_after` on `RestRateLimitedError`. The names are
interface — one is added, never renamed — and a test holds every raise in
the library to a named reason, so `unknown` only ever comes from code
elsewhere. The full table is in docs/API_REFERENCE.md.

Two things were fixed on the way:

- **REST and MQTT now diagnose a certificate failure as login does.** Both
  still said "almost always a temporary problem on iRobot's servers … not
  something wrong with your setup" for every certificate failure — the
  claim login had dropped after a field report showed it wrong for a local
  trust store. Now one diagnosis, three reasons.
- **MQTT no longer raises a builtin `ConnectionError`** in the one place it
  did, past every `except CloudError`.

## A time limit on every request

The library set none. aiohttp sets none by default either, so a server that
accepted a request and never answered held the caller indefinitely.
ha_roomba_plus protected itself; every other caller was exposed.

Every HTTP request now has **30 seconds**, from sending to having read the
whole answer. `login()`, `CloudAccount.login()` and every REST client take
`request_timeout=` (`None` for no limit). A 403 relogin runs outside it, so
a slow login does not use up the request's time.

## No secrets in `repr(LoginResult)`

The typed fields of a login kept every secret out of their `repr`. `raw`,
the whole login response, put them all back: every robot's password, the AWS
`SecretKey` and `SessionToken`, the IoT tokens — in any log line, test
failure or dump that showed the object. `raw` is out of the `repr` now; the
data is unchanged for a caller who asks for it. A test plants a marker in
every secret of a real login response and looks for it in every `repr`.

## Two forms kept on purpose

For mission history, favorites and the part-counter write, the Prime client
already had the form the **Prime** app uses. Nobody has shown that those work
on a Classic robot, so each client sends its own generation's form.

**`roombapy-prime-verify-classic-cloud`** (tools) measures it on a Classic
account:

- `--compare-reads` — mission history in both forms, including one page of
  paging; favorites with and without `app_edition`; the part counters.
  Changes nothing.
- `--reset-part-with-prime-body PART_ID` — **only for a part you have just
  replaced.** Resets it with the Prime body; if that does nothing, resets it
  with the Classic body, so the part is reset either way.

A working Prime body would also be the first measurement of
`reset_robot_parts()`, which is inferred from the app's code and has never
been sent.

## Housekeeping

- **`mypy --strict`** is the CI gate now, pinned to mypy 2.3.1. Getting there
  is what found the malformed-login gaps above.
- **Coverage is gated per module**, on every Python version: 95 %, or for
  the eight modules below that today, at least what they have now — listed
  by name in `scripts/coverage_floors.json`, and the list may only shrink.
  `vendor_reference.py` ships in the package and no test had ever loaded
  it; it has its tests now. `mqtt_client.py` rose from 88 % to 97 % with
  the tests for `reason` and is off the list.
- **Releases are marked by their version.** The release workflow published
  every tag as a full release, so this beta would have shown as "Latest". It
  now also refuses a tag that does not match `pyproject.toml` before anything
  reaches PyPI, where a version cannot be replaced.
- **`examples/classic_cloud.py`**: one login, then maps, mission history and
  part counters for every Classic robot on the account. Reads only.
- README and the PyPI description say what the library is now; Python 3.14,
  tested in CI since 0.3, is declared.
- A `.gitignore`, and `tools/build/` removed: fifteen stale copies of the
  scripts, committed by mistake in 0.3.1.

## Not in this release, on purpose

- **The MQTT transport (aiomqtt)** is 0.5.0, on its own branch, with no
  features next to it.
- **`PrimeRobot`'s own relogin** moves onto `CloudAccount` with it: the relogin
  it keeps is for the MQTT token, which 0.5.0 rewrites.
- **Splitting `rest_client.py` and `prime_robot.py`** waits for 0.5.0 too,
  which rewrites most of `prime_robot.py`. Splitting first would move the
  same code twice.
- **One naming rule for raw and parsed answers** — `x()` parsed, `x_raw()`
  raw — breaks callers of the methods that do not follow it yet, so it
  belongs to 1.0.
