# roombapy-prime 0.3.0b11

Cross-checked against an independent reconstruction of the same protocol
and against two more app versions. Two things here were wrong.

---

## The firmware catalogue was on the wrong host

`get_firmware_raw()` called the SigV4 gateway and got a 403. That was
read as "the path exists, the consumer role has no invoke rights" and
recorded as settled — correct reading, wrong conclusion.

The catalogue is on `content-prod.iot.irobotapi.com` and needs **no
authentication at all**.

**It also took the wrong parameters.** App 3.0.0's `FirmwareRequest`
declares six, not four:

```
required:  sku, softwareVer
optional:  track, dockFwVer, dockFwVerSec, dockHwRev
```

The optional four are sent only when set — passing `track=prod` and an
empty `dockFwVer` unconditionally was a guess about defaults. And
`dockFwVerSec` and `dockHwRev` are missing from the reference
implementation too.

## MQTT in-flight limit raised to match the app

paho defaults to 20 unacknowledged QoS-1 messages; the iRobot app sets
1000. This matters for `_subscribe_and_wait`, which subscribes to every
persistent topic in one loop — beyond twenty, the rest queue behind the
window and can look like a missing SUBACK.

## New: check whether a robot still answers locally

```
roombapy-prime-verify-local-channel
```

App 2.2.4 carried a complete local API — 46 socket serializers,
`irobotmcs` discovery, port 5678. App 3.0.0 has none of it. Whether a
given **robot** still listens is a question about its firmware, and
nobody has asked it.

Four stages: UDP discovery, TCP connect, TLS handshake, and deliberately
**no** MQTT CONNECT. No credentials, no cloud, nothing sent to the robot
beyond the nine-byte discovery broadcast.

The discovery reply carries SKU and firmware version — the datapoint the
whole question turns on. A run that gets that far and then fails has
already produced something useful.

## New: a third possible source of region names

`get_map_version()`, `parse_map_version_regions()`,
`get_map_region_names()`.

Marked unverified, and honestly: app 3.0.0 does not call this path, 2.2.4
has it only under the older `pmaps` naming, and `geojson_details` appears
in **no** app version checked. Kept because "not in the app" is not "does
not exist" — a server routinely serves what a newer client stopped
calling.

Likely moot, though: 2.2.4 resolved region names one at a time from map
metadata, and a tester's real bundle carries them in the standard
`cleanZones` GeoJSON layer, which this library already reads.

## mypy now runs in CI

Against production code, at default settings — not the whole package,
and not `--strict`. Both limits are deliberate:

```
full package, --strict      1399 errors
production code, default      33 errors
```

Gating on the larger number would mean gating on nothing: nobody clears
1399 errors before a release, so the job would be switched off within a
week. 33 is a number someone can work through. The path from here is in
the workflow comment — reach zero, then add tests, then `--strict`.

**It paid for itself on the first run.** Four dataclass fields in
`map_bundle.py` were declared twice, with different comments. The second
declaration silently won, and the first block's documentation described
a field nobody read. `no-redef` sees that; no test can.

## Documented

- **`reset` is the reboot command.** `device_restart_page` →
  `ControlSettingsRepo.restartDevice` → `MissionCommandType.reset`
  (index 7), same send channel as `start`.
- **`editv3` map editing over MQTT** — nine operations, with the
  `delPermanentAreaRes` trap: eight replies end `Rsp`, one ends `Res`.
  Not implemented; the REST path is now field-confirmed.
- **The local channel existed and was removed** between 2.2.4 and 3.0.0.
  It would not have answered the `async-dependency` question anyway: the
  reference implementation still logs in to the cloud once to fetch the
  robot's local password.
- **`na-irbtfeatures`** added to the shadow validation run despite
  appearing in no app version — a shadow `get` either answers or does
  not, and testers settle it as a side effect.

## Documentation

- **`edit_map()` is confirmed working.** A field tester's rename-and-
  revert run came back 7 OK, 0 failed, both steps verified in the app.
  It had never once been exercised against a robot — the changelog said
  *confirmed via bytecode, not yet wired into* anything. It was never
  broken, just never run.
- **Zone names are in the map bundle**, in the standard `cleanZones`
  GeoJSON layer, confirmed on a real robot. The `geojson_details`
  endpoint the reference implementation points at was never needed.
- The README now documents the local-channel check, and the API
  reference carries the corrected firmware call, `reset`, and
  `edit_map`'s new status.

## Upgrading

```bash
pip install --upgrade "roombapy-prime@git+https://github.com/johnnyh1975/roombapy-prime.git@v0.3.0b11"
pip install --upgrade "roombapy-prime-tools@git+https://github.com/johnnyh1975/roombapy-prime.git@v0.3.0b11#subdirectory=tools"
```

The Home Assistant integration pins this version from 4.0.0a42 onwards;
tag this release before that one, since its release workflow checks the
pinned version exists.
