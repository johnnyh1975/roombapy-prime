# roombapy-prime 0.2.0b6

b5 fixed one of two code paths carrying the same bug. This is the other one, found by sweeping for
the first.

## `verify-writes schedule_create_delete` could not run on any account

The check derives its payload from an existing schedule — deliberately, because an earlier version
built one from a name and nothing else and got HTTP 500 from a real server, which was then reported
as "create_schedules does not work".

It found that template with `getattr(schedule, "options", None)`. `SchedulesList.schedules` is
`list[dict]`, so that returned `None` every time. `template` was always `None`, the check always took
the "this account has no schedules" branch, and it never sent anything.

These were the two code paths that told one tester he had no schedules while his app showed three.
b5 fixed the listing path and rewrote this branch's *wording* — which made the message clearer while
leaving it exactly as wrong.

## An unreadable response is no longer reported as an empty account

When the server sends schedules and none of them parse, the check now says so directly and names it
as a bug here. Telling a tester he has no schedules sends him to create one he already has, which is
how this went wrong twice.

It reads through `get_schedules_raw()` for the same reason `schedules` does: a parsed response cannot
be used to find out whether the parser is dropping something.

## Quiet hours: a resend that was not what it claimed

`_set_dnd` read `getattr(current, "raw", None) or fields`. `DNDStatusResponse` is a frozen dataclass
of four fields with no `raw` among them, so the fallback was the only branch that ever ran. The line
implied a fidelity the check does not have.

Now explicit: the resend is reconstructed from the parsed model, so anything the server sends under a
key this project does not model is dropped. Fixing that properly needs a raw DND accessor, which is
not invented here without a reason to.

## Every household-scoped check now says which household it picked

`get_household_id()` chooses the household containing this robot. On an account with a Classic and a
Prime robot there is more than one, and an empty answer from the wrong one looks exactly like an
empty answer from the right one — the ambiguity behind three rounds of field testing now.

`schedule_create_delete` and `set_dnd_settings` both print the id and whether it was resolved or
passed with `--household-id`.

## Two more, from this release's own bug hunt

Both are the same failure the release is about, one level down: a shape nobody expected, handled by
raising instead of by saying so.

- `_create_and_delete_schedule` read `(raw or {}).get("household_schedules")` — b6's own new code —
  which raises `AttributeError` on any truthy non-dict. A crash there takes down the diagnostic
  output this release exists to produce.
- `SchedulesResponse.from_json()` iterated `household_schedules` without checking it is a list. A
  dict there yields its **keys**, and `SchedulesList.from_json()` then called `.get()` on a string.
  This is in the library, not the tooling, and on the path Home Assistant's schedule calendar and
  switches use — an error envelope reaches exactly that line.

Both now return nothing instead of raising. Seven response shapes are covered by tests: bare list,
string, `None`, error envelope, non-list containers, non-dict container entries, non-list schedules.

## Tests

`verify_writes.py` had static tests only — signature matching and source grepping. Every signature
involved was correct; that is why three of these survived. The runners now have tests that execute
them against realistic server responses.

937 tests passing.
