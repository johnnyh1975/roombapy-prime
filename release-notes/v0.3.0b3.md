# roombapy-prime 0.3.0b3

Field reports, a bug-hunting round, and one wall that turned out not to be one.

## Favourites arrive in two shapes and only one was handled

@chairstacker downgraded to Roomba+ v3.5.1 by accident and found the favourite buttons he
had been missing on the alpha. Same account, same endpoint, two answers.

Both versions call `GET /v1/user/favorites`. The Classic path does:

```
result if isinstance(result, list) else result.get("favorites", [])
```

This side returned `[]` for the object form. **That unwrap has been in the Classic path
since it was written**, so the wrapped response is not new server behaviour — this side
simply never handled it. His favourites were being fetched and thrown away.

Nearly missed: the first theory was the `app_edition=1` query parameter, which only the
Prime path sends. The answer was in our own repository, in the path he had just proved
works.

## A region command could name no room

`Region.from_json` turns a server-sent `null` into `""` — the `.get(key, "")` shape a
default cannot tell from an absent key. The result is a command that names a room and does
not, which is @Echovictor37's whole-house clean one field over. Refused now, with an error
that says what would otherwise have happened.

## 91 parsers raised on unexpected input

A truncated download, a server error body, a `None` where a feature was expected. **A
parser that raises on those turns a bad response into a crash in the caller's code.** They
return an empty instance now.

Twenty-two still raise, deliberately: the GeoJSON features have required fields and cannot
construct an empty instance. A feature with no id and no geometry is not an empty feature.

## `reconnect(fresh_client_id)` did nothing

The client-id rotation was tried in b2 and is reverted here — the id comes from iRobot's
login response and the broker expects that one. A derived id does not connect at all.
The parameter stayed behind after the revert, so a caller could pass `True` and get
nothing. Removed.

## The Dart snapshot is readable after all

Recorded twice in this project as a wall. It is not: `blutter` plus a locally built Dart
3.9.2 VM produces the object pool, and every settings enum with its index and wire value.

That answers the last open question on issue #46. Writing a wash-frequency setting is
**one field per user action** — `_updateWashFreqByType` is a type switch on the value's
class, not three chained writes. Picking "Medium" writes `pwReturn = 101` and nothing
else, because mode and level share one field.

@chairstacker warned on 1 August that a control writing one field where the robot expects
two would produce a setting that is accepted and does nothing. It was the right question,
and the answer is no.

The value sets came out with it — `padDryDur` is `[2, 3, 4, 5, 6]` hours with no series
split, which contradicts both the 2.2.4 table and what this project told two testers
yesterday. Written up in `docs/internal/SETTING_VALUE_SETS.md`, including that the same
document has now said four different things about these values.

1,256 tests passing.
