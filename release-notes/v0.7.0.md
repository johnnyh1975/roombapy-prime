# roombapy-prime 0.7.0

A test for accounts with two or more Prime robots, and two fixes to what
the diagnostic scripts report. No change to the library's own behaviour
towards a robot.

## Can one connection serve every Prime robot? (#91)

Two Prime robots on one login connect with the same server-issued client
id, and AWS IoT drops the older connection when a second one arrives with
the same id. @mattdrmc's Combo j4+ and Roomba 505 knocked each other off
about 3,500 times an hour.

One remedy is one MQTT connection per account that carries every robot's
topics. Whether the iRobot cloud allows that is the question this answers
first:

```bash
pip install roombapy-prime-tools==0.7.0

roombapy-prime-verify-shared-connection --token-only   # seconds
roombapy-prime-verify-shared-connection --find         # about 75 minutes
```

1. **What the login's tokens cover.** For each token, the robots named in
   its claims and in the response's list. Passes when one token names
   every Prime robot on the account.
2. **One connection for all of them.** It subscribes to every robot's
   shadow updates and asks each robot for its shadow every five minutes,
   across the token refresh. It passes when:
   - every subscription is accepted;
   - every robot answers, before the refresh and after it;
   - nothing drops the connection.

   The run extends itself if the refresh would fall after its end.

It logs in once and reads shadows only. With `--find`, and after a yes,
each robot plays its sound at the start and after the refresh. It prints
no password, no token and no client id (only a fingerprint that says
whether two are the same). Robot ids appear as their last four
characters, in the library's warnings as well.

## `--output` and `--dump-config` are written again

`verify_named_shadows`, `verify_mission_commands`, `verify_map_edit` and
`verify_mission_timeline` printed their report and then stopped: since
0.1.11a25 their `main()` handed the run's result to `sys.exit()`, which
never returns. The report file, the redacted capture and the issue link
were never produced, on every successful run, with no error.

They are written again. `_cli.run_and_keep()` returns the exit code and
the run's result together; a failed run still exits with its code and
writes nothing. The final summary is no longer printed a second time.

## `Report.summary()` counts the short status forms

`Report.add()` has accepted `"FAIL"` and `"SKIP"` beside `"FAILED"` and
`"SKIPPED"` since the short forms crashed two testers' runs. `summary()`
counted only the long forms: a check added as `"FAIL"` printed its cross
above "0 failed", and `roombapy-prime-validate`, whose exit code comes
from that count, reported success. Both forms count now.

## Tested

- 1394 library tests and 561 tool tests pass on Python 3.13 and 3.11;
  ruff passes.
- The new tests fail against 0.6.0:
  - the five `--output`/`--dump-config` runs write no file;
  - `summary()` counts one failure of two.
- The shared-connection script's tests fail when:
  - a token refresh counts as a drop;
  - answers from before the refresh count after it;
  - the token's claims are ignored;
  - robot ids are printed in full;
  - `--find` runs without its prompt.
- The script has not run against a real account yet. That is what
  @mattdrmc's run is for.
