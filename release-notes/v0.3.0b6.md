# roombapy-prime 0.3.0b6

Required by Roomba+ **v4.0.0a35**. No breaking changes.

A short release, and three of its four items are corrections to things this
library told testers that were not true. That is worth saying plainly, because
two of them cost people hours.

## The log only ever reported bad news

The MQTT drop logged at WARNING. The reconnect that followed it logged at INFO.
At Home Assistant's default level you saw the failure and never the recovery —
so a successful reconnect and a dead subscription produce exactly the same
thing on screen: nothing.

@ratpic83 read that silence as a subscription that never came back, filed it as
the issue making the integration unusable, and spent two hours on it. Then he
turned INFO on and retracted it himself: the subscription recovers, his robot
ran a full job, and the state was correct throughout.

A resolution now logs at the level of the problem it resolves.

## The disconnect warning claimed a cause it could not support

b5 added a warning after three drops in five minutes, naming a same-`client_id`
collision — the iRobot app and this library evicting each other — as the
explanation, with "closing the others is the test".

@ratpic83 ran that test. He force-quit the app on every phone in the household
and the drops continued: roughly 82 and 55 minutes apart, recovering on their
own each time, while the robot completed a job and docked correctly.

That spacing reads like a session lifetime rather than a race. Eviction is now
"the first thing to rule out" instead of the answer, and the message points at
the recovery line, because a drop is only alarming if nothing follows it.

**What still points at eviction is frequency.** A session lifetime does not
expire every few seconds; several drops inside five minutes is a different
phenomenon from one an hour, and worth naming when it happens.

## `settings_roundtrip` was wrong about every dotted key

```
audio.volume          write ok   read_back_matches: False
audio                 write ok   read_back_matches: True
padWetness.padPlate   write ok   read_back_matches: False
padWetness            write ok   read_back_matches: True
```

Two keys failing while their parent maps pass is not a robot refusing dotted
addresses. It is `after.get("audio.volume")` on a document where `audio` is a
nested map — the same bug `_resolve_probes()` was fixed for in b4, one step
later in the same function.

So no dotted write has ever been confirmed by this tool, and none has been
disproven either. With the comparison fixed, a dotted write that genuinely does
not stick will now say so.

## `custom_initiator` asked for something impossible

The check wanted two observations: does the robot chirp, and does the cleaning
history afterwards name Home Assistant. **`find` is not a mission and creates no
history entry**, so the second could never happen.

@chairstacker reported a chirp with no history entry and apologised for the
partial result. He had answered the question completely: **the server accepts an
initiator that is not among the vendor's 25**, so the field is a free string
rather than a registry, and this project can identify itself instead of
impersonating the local iRobot app.

The check now asks for the chirp and nothing else.

## `DigiCap` had two fields and the vendor declares eleven

`v3_capability_gates.json` lists eleven `digiCap.*` gates. This class modelled
the two that happened to appear in one capture — `appVer` and `timeline` — so
nine gates the vendor declares were unreadable through this library:

```
cwia · cleaningProfiles · cte · digiSpot · ddAutomation
petFurniture · kozRecommendations · perspective3DMap · smartClean
```

Modelled from the gate table rather than from a capture, which inverts this
file's usual rule and is deliberate: a gate that no robot in hand reports is
exactly the one nobody can discover by looking. `None` on every robot seen so
far is the honest answer, and it distinguishes "not reported" from "reported
off" the way every other capability does.

## Upgrading

```
pip install --upgrade "roombapy-prime@git+https://github.com/johnnyh1975/roombapy-prime.git@v0.3.0b6"
```

Roomba+ v4.0.0a35 pins this version. If you run the integration, upgrade both.
