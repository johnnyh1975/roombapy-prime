# roombapy-prime 0.3.2

Two new stages for the virtual-wall tool, and the documentation fix that
turned up while looking for them.

## The virtual-wall tool can finally change something

Every confirmed write on this path has resent the existing zones
**unchanged**. `set_virtual_wall` replaces the whole shared list, so what
happens to a list that is missing or moving an entry has never been
observed — and that is the case a user hits the first time they delete a
keep-out zone.

Stage 2 was deferred for months on the grounds that it "would need a
real, user-supplied polygon geometry to add". That is true of **adding**,
and it is not true of removing or moving. Both are the current list with
existing coordinates preserved byte-for-byte, so the unconfirmed
CommandPolygon coordinate system is never touched. What made stage 2 look
risky was only ever half of it.

**`--drop-one-wall`** sends the list minus one entry, re-reads to check
the removal actually stored, then puts the entry back.

**`--move-one-wall`** shifts one zone, pauses so you can look at the app,
then moves it back.

Both capture the original list **before** sending anything and print the
restore payload before the change, so a run that dies partway still
leaves you the exact body that repairs the map. A map with fewer than two
walls is refused by `--drop-one-wall`: removing the only entry sends an
empty list, which asks a different question and would be
indistinguishable in the result.

## `--move-one-wall` measures the coordinate system

`policy_zone_to_virtual_wall()` passes geometry through unchanged —
confirmed by native analysis, no transformation anywhere between the
bundle read and the wire. So the numbers in a command *are* the numbers
in `policyZones.geojson`, and adding a constant moves the zone by that
amount in whatever unit that file uses.

Which means the unit never has to be known in advance, and can be read
off afterwards: move a zone by a known delta, look at the app, and the
observed distance against the delta gives the scale. **Metres or
millimetres has been open on the edit path since it was first modelled.**

The delta defaults to a quarter of the zone's own longest side — visible
in the app, and unable to leave the floor plan whichever unit it turns
out to be. A fixed number would be either invisible or off the map
depending on the answer to the question being asked.

The run stops after the move and waits, because that is the only moment
the moved zone exists. The restore puts it back and no re-read can say
what it looked like.

## Four documentation blocks were not documentation

`send_simple_command()` carried two triple-quoted blocks in a row. The
first is the docstring; the second was a bare string expression —
evaluated and discarded. It held the whole evidence trail for the
corrected mission-control path, including the independent third-party
corroboration, and `help()` never showed a word of it.

Three more turned up in `mission_control.py`, `schedules_dnd.py` and
`mqtt_client.py`, one of them the correction of four wire keys. All four
are merged into their docstrings, and a test now fails on the pattern.

It excludes PEP 258 attribute docstrings, which are legitimate and which
the first version of the check flagged — "fixing" those would have been
the opposite of an improvement.

## Also

`irbtTopics` / `iotTopics` are confirmed twice over now: from a field
capture and independently from the app's own service-discovery response.
The note calling them best-guess names is gone. They stay optional
reads — but for a different reason than before: the **value** is
legitimately absent sometimes, deployment-dependent, and the vendor's own
app carries error causes for both being empty.

Python 3.14 is in the CI matrix. The suite was already passing there;
`requires-python = ">=3.11"` promised it either way, so the promise and
the evidence now match.

The README carries PyPI version, Python versions, downloads and license
badges.
