# roombapy-prime 0.3.0b13

One payload fix that matters more than its size, and a round of
removing status banners that had outlived their truth.

## `regions: []` should never have been sent

An empty region list produced `regions: []` in the command payload,
because `[] is not None`.

The vendor app omits the key entirely for both null and empty —
verified from `MissionCommand::toPayload` in Prime 3.0.0, which
null-checks the list, then checks its length, and skips emitting the key
on either. Scope is decided downstream by whether region data is
present.

So `regions: []` is a shape the vendor client never emits, in the one
place this library cannot afford to be creative: the difference between
cleaning a room and cleaning a house.

## A race in MQTT dispatch

`_on_message` runs on paho's network thread and iterated the
persistent-subscription dict live, while `subscribe()` and
`unsubscribe()` wrote it from the caller's thread. The resulting
`RuntimeError` escaped into paho's dispatch loop — after which **every
watcher on that client stopped receiving, silently**, with the
connection still looking healthy.

Reproduced deliberately before fixing. If you watch both a live map and
a timeline on one client, that is exactly the shape it needed.

## Questions closed that no field tester could have closed

A tester sees one robot, and silence is ambiguous — "not observed" is
not "does not exist". Firmware 3.8.126 answers by enumeration:

**The dock report family is exactly `{evac, refill, padwash, paddry}`.**
No `charge`, no `battery`. From the subscribe-list construction itself,
not a pattern match across the image.

**Eight unproven `DoneCode` values are not in 3.8.126.** The six
confirmed ones each occur exactly once, contiguous in a single 31-byte
window. The eight are kept as enum members — the check covers one
firmware version and this library supports robots several generations
back — but they must not be cited as firmware-backed.

## Region cleaning, confirmed on hardware

@bryznnguyen fired it on a Combo 105: `START` with a non-null `map_id`
and one `Region(RID)`. The mission ran 27 minutes and covered 234 sq ft,
against two prior whole-house runs at exactly 644.

The area is the proof. An acknowledgement proves delivery; only the
area proves intent.

His own caveats are recorded as caveats: the outbound `initiator` is
confirmed, the echoed one is not, and the geometry was not
independently audited.

## `command_type=START` is not a scope limiter

Disassembly of `process_robot_command` shows a dispatcher plus an
operating-mode gate — it does not contain the region-vs-global branch
at all. START says what kind of run this is, not how much of the house
it covers.

That run worked because a region was named. There is no `clean_all`
field in the firmware; whole-house is the *absence* of a region
selection.

## Also

- **`SplitRoomV1` / `MergeRoomsV1` confirmed on hardware.** The merge
  command's wire name is `arrange_room` — now attested in app bytecode,
  on a live robot, and in firmware. Nobody should "fix" it.
- **`condNotReady` is `list[int]`**, and the parser filters rather than
  casting. The individual code meanings stay unnamed.
- **`get_firmware()`** parses the catalogue. An empty list means the
  catalogue had nothing for that sku, not an error.
- **mypy is clean and the CI gate is hard.** The 34 errors it had been
  running past included one real crash path.

## Status banners removed

Three modules opened with "STATUS: Draft" and a claim of never having
been tested against a real account. `rest_client` went further: "not a
single one of these calls has actually been executed yet."

A dozen testers had been using all three for months.

The specific caveats stay exactly where they were — `clean_all`, the
p2map upload, the services write path. A blanket disclaimer at the top
of a file invites either ignoring it or distrusting everything, and
helps nobody deciding whether one particular call is safe.
