# roombapy-prime 0.2.0b15

Works with Roomba+ **v4.0.0a28** — no integration update needed, nothing here changes what the
integration uses.

Everything in this release comes from the first real `settings_roundtrip` run (@DaRealGuGu, on b14).
The read worked; what happened next did not.

## The volume key was a guess, and the guess became a claim

The probe list looked for `audioVolume`. The robot calls it **`audio`** — and our own comment beside
that entry said the name was guessed.

So the check reported "not on this robot" for a setting the robot plainly has. **A guessed name in a
probe list does not merely fail to find its field; it reports the field as absent**, which reads as a
fact about somebody's hardware. Second time in that file a wrong name became a wrong claim about a
tester's robot.

Five of the six controls are present on his N185240, not four. `chrgLrPtrn` really is absent.

## Reading a shadow twice re-subscribed to topics it already held

`get_shadow()` subscribed on every call and never unsubscribed, so a second read of the same shadow
in one session re-subscribed to topics the broker had already granted.

That redundant step is what failed: his second `rw-settings` read got no SUBACK within three seconds
and then no response within eight, while the first read in the same session had worked.

The subscription is now skipped when the topic is already held — **a step deleted rather than a retry
added**. The bookkeeping is cleared on disconnect, because a new session grants none of it, and
keeping it would make the next read skip a subscription it no longer has.

The SUBACK guard stays meaningful for a first subscription, where an unacknowledged one really does
mean a topic that will deliver nothing.

**Note on what this does not fix.** Whether the interactive pause kills the connection outright is
still open — that needs a debug log showing whether paho reports a disconnect between the two reads.
Nothing has been added that reconnects on a missing SUBACK: a reconnect drops every existing
subscription, and doing that on a slow broker would produce exactly the symptom this project has
spent a week chasing.

## The settings check asks everything before it writes anything

The prompts used to sit between two MQTT operations, and his run failed on exactly the operation
after one. A run should not depend on how fast somebody types.

It also fixes a worse property: prompting per field meant the first failure ended the run. He
answered one question, it failed, and the other four probes were never attempted — six fields with a
question each is six chances to lose the remaining ones. A refused write now moves on to the next
field.

## Favourites never parsed, so nobody had any

`_favorite_from_json()` read `favorite_id`. **The same model's own `to_json()` writes `favoriteid`** —
one file apart, no underscore. Same for `commanddefs`, and for `default`, `deleted` and `hidden`.

Both sides were written from the app's source and neither was checked against the other. The parser's
own docstring admitted it: *never seen a real server response*.

**A favourite whose id does not parse is dropped by the caller**, so the mismatch produced no error —
it produced an account with no favourites. @chairstacker has seven and saw no buttons for them, and
reported it as a missing feature. The buttons had been built for weeks.

Sixth instance in four days of the same shape: a name that disagrees across a boundary, an exception
or an empty result swallowed, and a symptom that reads as "there is nothing here".

Both spellings are now accepted, the app's own first because it is the one with evidence behind it. A
test pins that order — the first version had it backwards while claiming otherwise.

## `clean_score` has a direction

Settled by an eleven-room account (@jouwdan) after a four-room one had looked ambiguous:

```
mission 33 (just now)   0.0, 0.0, 0.0   last_updated_by: batch_decay_skipped
mission 32              0.15, 0.1744, 0.1744
mission 27              0.2801, 0.4
mission 25              0.4201
mission 12 (long ago)   0.6973
```

**Higher means dirtier.** Rooms cleaned by the newest mission read exactly zero, with decay skipped
because they had just been reset; the room untouched since mission 12 approaches
`clean_score_ranges: [0.7]`, which makes that threshold "needs cleaning".

The four-room account looked contradictory because two of its rooms shared a mission and differed
anyway — room size and traffic move the rate, not the direction.
