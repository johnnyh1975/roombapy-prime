# roombapy-prime 0.3.3

Two live-map bugs that both ended the same way: a stream that had
stopped, reporting success. Both came from one field report.

## The live map died after the first reconnect

`watch_live_map()` subscribed to its MQTT topic **exactly once**.

The client clears `_subscribed_topics` on disconnect, deliberately -- "a
new session grants nothing" -- which leaves re-subscription to the
caller. `_watch_topic()` does that for every other stream in this
library. This one did not.

So after the first reconnect the subscription was gone and nothing
noticed: an empty queue, no exception, no counter movement, and a
keep-alive still reporting success because the REST ping is a different
transport entirely. Permanently dead, silently.

This needs no unusual conditions. One reconnect is enough, and
reconnects happen on their own -- one tester's instance does it on a
55-minute cycle, so the map would have died within the hour, every hour.

It also explains a report that had been attributed to a missing
`irbtTopics` prefix: every live-map counter at zero mid-mission with
nothing wrong anywhere (@chairstacker). That explanation needed the
prefix to be absent. This one needs nothing.

The stream now watches for the drop alongside the queue and takes its
subscription back, retrying until it succeeds. The reconnect itself is
still owned by `_watch_topic()` -- two coordinators on one connection
would be worse than the bug.

## The keep-alive hammered a rate limit

@jpatchMC ran two Prime robots on one account and got:

```
RestError: HTTP 429 from .../v1/p2maps/livemap?robotId=...
```

On a failed ping no message arrives, so the stream expiry is never set,
so the delay falls back to a flat ten seconds -- against the endpoint
that had just said there were too many requests. Two robots, two loops,
**twelve requests a minute**, indefinitely.

That explains what he saw: one robot's map and status going quiet while
the other kept working, and commands succeeding on both, since those
travel over MQTT and never touch this endpoint.

Now: exponential backoff from the first failure, capped at five minutes,
with a floor of one minute for a 429 specifically. **A rate limit is a
statement about the account, not about one robot** -- another watcher is
asking too, and both have to give way or neither recovers. The warning
names the status code and the wait.

## A lockout no longer tells you to check your password

Gigya locks an account after too many login attempts and clears it
itself in minutes. That reached Home Assistant as an authentication
failure, so the owner was asked to re-enter their password -- and every
attempt at that is another login against a locked account. @jpatchMC
went as far as resetting his password several times to rule out a wrong
one, each reset feeding the thing he was diagnosing.

The message now leads with not re-entering anything, and says to wait.

**The classification deliberately did not change**, which looks
backwards and is not. Raising a rate-limit error instead would reach
Home Assistant as "not ready", which retries on `2 ** min(tries, 4) * 5`
seconds: 11 attempts per config entry in ten minutes, 22 across his two
robots, against an account locked for too many attempts. The
credentials path produces zero automatic attempts. Against a lockout,
stopping is correct and the retry loop is the harmful one. Measured,
then written down, with a test that fails if anyone reverses it.

## Also

**`--drop-one-wall` verified the wrong map.** It re-read the map version
passed on the command line, while every accepted edit mints and returns
a new one -- so it reported "ACCEPTED BUT NOT STORED", its loudest
warning, for an edit that had worked. @chairstacker watched the zone
leave the map and come back in the app and reported that too, which is
the only reason it was caught in one round. It now reads the version the
edit returned.

**`CommandPolygonMetadata.from_json()` raised on malformed input.** The
guard was `return cls()`, and `furniture_id` has no default -- so the
safe path raised `TypeError`. It returns None now, which is also the
honest answer for a robot with no furniture: @chairstacker's Combo 405
creates none, which makes ad-hoc zones structurally unavailable there
rather than merely untried.

**Vendor firmware schemas** are in `docs/internal/` as a reference, with
a guard comparing this library's enums against them. It resolved `wid`,
whose wire value had been recorded as unresolvable, and turned up `tag`,
which appears nowhere in the app. Read its `_channel` note before using
it: these are Classic, local-channel schemas, and comparing them against
cloud structures has already produced one wrong conclusion.

**`check_vendor_value_sets.py` now runs in CI.** It had been in the
repository for months, passing locally and checked by nobody.
