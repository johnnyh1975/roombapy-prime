# roombapy-prime 0.2.0b11

One new check, and it could unlock six controls that nobody has today.

## `settings_roundtrip` — resends every setting at its own value

`set_setting()` writes to the `rw-settings` shadow and is confirmed end to end for `childLock`: the
write was accepted, read back, and the robot said so out loud. Four more fields were written and
read back successfully but have no observable effect to check against.

Nobody has tried the fields iRobot's **own product profiles** list as user settings. Those profiles
turned up in the app's raw resources and cover twelve product families:

```
chrgLrPtrn      charge light ring pattern    [0, 1, 2]
audioVolume     audio volume                 [0, 100, 1]
padDryDur       mop dry duration             [4, 6, 9, 12] hours
pwAreaInterval  pad wash frequency           [5, 10, 15]  (x10 sq ft)
evacAllowed     auto-evacuation allowed      boolean
autoevacFreq    auto-evacuation frequency    integer
```

The value sets are the vendor's own, and @chairstacker's diagnostics confirm two of them
independently: `padDryDur: 12` with the app showing 4/6/9/12 hours, `pwAreaInterval: 5` with the app
showing High at every 50 ft².

`chrgLrPtrn` is the one whose **read and write syntax the profile records outright** —
`"set": {"chrgLrPtrn": %d}` — where 76 other settings carry a literal `"TBD"`. That does not mean no
command exists: @chairstacker changed both mop settings through the app and has the files to prove
it. It means the profile author did not fill it in.

**Every write resends the value the robot already reports.** Nothing changes, so a success proves
the path and a failure costs nothing — the same shape as the DND and favourites checks.

## The one thing a green line does not mean

`schedHold` accepts a write, reads back changed, and the robot ignores it completely: the schedule
stays active in the app. So this check can only say **the write was accepted**, never that the
setting works. The check asks testers to open the app afterwards for exactly that reason.

## Two guard tests caught this before it shipped

The first version did not pass `connect_mqtt=True` at the connection site, which would have failed
only against a real robot. And its shadow unwrapping handled none of the three shapes correctly —
it produced the outer dict and would have reported "none of these settings exist on this robot",
a plausible negative result and the worst kind of wrong.

## The live map asked the robot to publish ten seconds too late — or never

`watch_live_map()` subscribes to the topic and then runs a keep-alive loop. The robot only publishes
while those pings arrive, and the loop **slept before its first ping**.

So the subscription was in place with nothing feeding it: `await queue.get()` on an empty queue, no
messages, no exception, no counter movement. And if that first ping failed, the handler logged a
warning and carried on — making the state permanent and completely silent.

A field capture showed exactly that: mid-mission, every live-map counter at zero, mission timeline
empty, and no error recorded anywhere. Everything else looked healthy, because the shadow watcher
uses shadow topics and needs none of this.

The ping now comes first, and consecutive failures are counted so one hiccup is distinguishable from
"this has never worked".

**The interval is still a stand-in and is now documented as one.** The app's own
`LiveMapKeepAlivePublisher` schedules against an expiration whose value has not been reconstructed;
ten seconds is 8,640 REST calls per robot per day, running whether or not anything is moving. Not
changed on a guess: raising it without knowing the real expiry would trade a cost problem for a
stream that dies mid-mission.

## The keep-alive is paced by the robot now, not by a constant

Every position message carries `update_expire_ts` — when the stream lapses unless asked again. The
app schedules its next ping at `expiration - now - refreshWindowMillis`, where that window defaults
to ten seconds. **It is a safety margin before the stream would lapse, not an interval.**

This library polled at a flat ten seconds, which is the same number meaning something else entirely:
8,640 REST calls per robot per day, running whether or not anything is moving. With a one-minute
validity window the same coverage costs about sixty.

`update_expire_ts` rides on the outer envelope beside `pos_update` and used to be discarded — the
inner object was parsed and the wrapper thrown away. It is now on `PositionUpdateMessage` as
`expires_at`.

Which unit the wire uses is not settled: the app types it as a Date, which says nothing, and no
capture carrying the field has been seen. Values past the year 2200 are read as milliseconds — a
threshold rather than a guess, since an epoch in seconds does not reach it for another 175 years.

The fixed interval stays as the fallback, for as long as the robot has said nothing and for robots
that never send the field. Pacing on a guessed expiry would risk the stream lapsing mid-mission,
and this project has just spent a week on one silent stream.
