# roombapy-prime 0.3.0b1

Required by Roomba+ **v4.0.0a31**.

## Why the version jumps

Seventeen beta iterations on `0.2.0` had stopped meaning anything, and this release changes enough
to deserve a new number:

- Three wire keys now read real values where they read `None` before. Code that checked
  `number_of_dirt_detects is None` and concluded "this robot does not report it" will start seeing
  numbers. That is a correction, and it is still a behaviour change.
- `to_json()`, `get_time_estimates()` and `reset_robot_parts()` gained optional arguments.
- `error_text` is a new concept beside `error`.

**What has NOT changed is the thing that matters most.** The write paths are still unconfirmed;
`settings_roundtrip` has never completed on any account. This number marks alignment with the
vendor's own model, not new maturity — read the transport section below before assuming otherwise.

## What this release is

A systematic comparison against iRobot's own app — `com.irobot.home.prime` 3.0.0, a Flutter rewrite
whose data layer ships as readable Kotlin serialisers — against 223 serialiser classes, 87 enums, 71
request classes and 25 locale files.

**Nothing here was failing.** That is the point: every fix below was invisible from the outside,
because a field read as `None` looks exactly like a robot that does not report it.

## Three keys that no robot has ever sent

```
read here              iRobot sends
numberOfDirtDetects -> dirt
staticMapId         -> map_id
coverageStrategy    -> covStrat
```

All three were readable guesses at what a field might be called. All three have read `None` on every
mission ever recorded — so the dirt-detection counter looked like something Prime robots simply do
not have.

## Four timeline event types were being dropped

`MissionEventDto` declares `cmd`, `disc`, `poly` and `tentativeLoc`. This library read `command`,
`discovery`, `polygon` and `tentativeLocation` — the readable forms, which `reloc` was already the
exception to. Both spellings are accepted now.

`futureEvents` was never read at all: finished events say where the robot has been, these say where
it is going.

## `coverage`, which answers a question this library reasoned about at length

`RoomInfoDto` and `ZoneInfoDto` both declare it, beside `area`, `passArea` and `totalArea` — all of
which were read. `RoomEvent`'s docstring spends fourteen lines working out whether `area` or
`total_area` means "how much was actually covered". The field that answers it was in the same
object.

## A callback could take down the whole connection

`_on_message` called handlers unguarded. A callback that raises kills paho's network loop thread,
and the connection then looks alive while delivering nothing — publishes queue and are never sent,
subscribes get no SUBACK.

**That is exactly what two testers reported.** @jouwdan's first read listed 21 keys and every
operation after it failed; @DaRealGuGu's run said "PUBLISH was queued but never sent" — the same
connection in the same state, seen from the other side.

This does not prove a callback raised on their accounts. It removes the only way one could take the
client down without saying so.

## The settings check was asking for keys the app never writes

`RobotServiceHandler.settingFromKey` is a switch over **24 individual keys**. Two of the candidates
this tool offered are not among them:

- `audio` should be **`audio.volume`** — the app addresses the sub-key with a dot rather than
  writing the whole map. @jouwdan's write of `audio` got no UPDATE response at all.
- `evacAllowed` is readable and sits in `rw-settings`, but the app does not write it.
  @DaRealGuGu's write of it was the one that failed on re-read.

Neither is proof — a robot may accept more than its app sends. But asking for a key the vendor never
writes, and calling the silence a bug, is how three testers spent a week on this check. Five real
candidates were added in their place, and a test now refuses any candidate outside the 24.

Also confirmed rather than changed: **one key, one value** is the vendor's own write shape, and
`padWetness.padPlate` is addressed directly. That retires the read-modify-write advice this project
carried — it described the *old* app's behaviour.

## The library can name an error

It had no error table at all: codes went through as integers, so `verify_region_commands` printed
`ERROR value=46` and left the reader to look it up — which meant asking us.

112 codes with iRobot's own title and explanation, in eight languages. `CleanMissionStatus` and
`DockStatus` carry `error_text` beside `error`; a code iRobot does not document returns `None`, so a
caller can say "error 236, undocumented" rather than "no error".

## Two naming conventions, and a switch that decides between them

`CommandDTO` carries `p2map_id`/`user_p2mapv_id` **and** `pmap_id`/`user_pmapv_id` as four separate
nullable fields — not as alternatives. A previous reading of the older app concluded the second pair
was obsolete. It is not: the app decides per device, through a flag sitting beside `isLegacySku` and
`isIrobotHomeClassicDevice`.

We cannot evaluate that flag, and a legacy-SKU robot receiving a command with no map it recognises
gets the failure @Echovictor37 documented — a PUBACK and a whole-house clean. `to_json()` therefore
takes `legacy_map_keys`, **off by default**: his confirmed clean did not carry the old name, and a
confirmed shape outranks a plausible one.

The same dual convention turned up on the read side: `RoomInfoDto` carries both pairs too, and only
the new one was being read.

## Spellings the field settled and the app did not

Four commands are camelCase in the app (`washPad`, `dryPad`, `stopEvac`, `stopPadDry`) and lowercase
here. **The lowercase forms are what a real robot recorded in its own shadow**, with a pad-wash
counter at 90 to show the washes were happening. They stay.

`point_clean` is the same story from the other direction: it appears verbatim in a favourite the
server returned, inside a routine named "Spot Clean". The app spells it `pointClean`. Both are
offered now — a server that stores one will keep sending it back, and removing the reader to tidy a
spelling would lose a working value.

`flrefill`, by contrast, appears in no capture anywhere. That one was a guess, and `fluidRefill` is
the vendor's.

## Types the key names could not tell us

The wire-key list names fields; a separate model dump types them. Checking 67 container fields
against this library found `targetSoftwareVer` modelled as a string where it is `List<String>` — one
firmware release can target several installed versions, which is what an upgrade path looks like.
Written the same day from the key names alone.

Everywhere else the types hold, which is worth stating: the models came through the vendor's rewrite
intact.

## Also

- **Schedule writes kept unknown server fields.** `is_smart_clean_fav` arrives on real schedules and
  appears nowhere in the app — read-modify-write was dropping whatever the server knows and the app
  does not, invisibly, because the request is accepted and the field simply stops coming back.
- **`schedule_id` is read from inside the options too.** 3.0.0 moved it there; a schedule whose id
  cannot be found is one nobody can edit, and that reads as an empty calendar rather than an error.
- **The mission timeline can be requested** rather than waited for: `{"timelineRequestId": <n>}` on
  the request topic, with the report carrying the same id back.
- **`startDoNotDisturb` / `stopDoNotDisturb`**, confirmed to carry no window — the period is set
  separately, these switch it ad hoc.
- **Twelve of thirteen `digiCap` flags** were being discarded, including `cwia` (whether iRobot's own
  presence cleaning exists on this robot) and `ddAutomation` (their demand cleaning).
- **`select_all` no longer travels with regions.** Nothing sets it, but @Echovictor37 showed what a
  misunderstood command costs: a PUBACK and a whole-house clean where one room was asked for.
- **`oModeStats`** — minutes and area per operating mode, in real mission entries and in *neither*
  the app's model nor this reader. The robot sends more than its maker's app declares.
- Firmware, dock refill state, pause timings, per-region names, `edgeOnly`/`quiet`, `wip`,
  `user_orientation_rad` and the six dock identity fields: all declared, none previously read.

## Three testers hit one transport wall, with three faces

```
@DaRealGuGu   PUBLISH queued but never sent
@jouwdan      no SUBACK, then no response
@utkjmitch    PUBLISH refused, paho rc=4
```

**@utkjmitch's session ties them together.** It was half alive: shadow subscribes dead, cmd-topic
publishes working, the robot physically obeying commands — one connection, one moment. Whatever
kills it does so between CONNACK and the first SUBACK, and paho notices only at the next publish. A
subscribe always loses that race; a bare publish fired quickly enough wins it.

That fits one thing better than anything else: **AWS IoT evicts the older connection when a second
arrives with the same client_id.** It also explains why a *first* read sometimes succeeds and every
later one fails, which a policy denial would not — a policy denies every time.

So the broker's own disconnect reason is now carried into both the SUBACK warning and the publish
error. This library recorded it and never showed it. And the tool says, **before** the run rather
than after it fails: close the iRobot phone app, and stop Home Assistant's integration if it talks
to this robot. Two of three testers reasonably concluded their hardware was at fault.

## A fourth way a command fails, and it is not about the payload

@utkjmitch's Y351020 ignored `start`, `stop`, `dock` and `find` for **61 hours** — each
broker-confirmed, each without effect, on fresh sessions and old ones. A finished "simple verbs are
dead on this SKU" report existed before the pattern showed itself: the robot's cloud document had
frozen after an errored mission, and every failure predated the power cycle that cleared it.

The three failure modes this project had recorded were all about payload shape. This one is not —
**the command is correct, the transport is correct, and the robot's own state makes it inert.**

His sentence is in the evidence trail verbatim: *a command test that fails on someone's robot can
pass an hour later, and neither result is wrong.* The warning now sits in `send_simple_command()`'s
docstring rather than in a document nobody opens mid-debug, with the check named — a phase stuck at
`run` while the battery climbs — so the next person can rule it out without reproducing 61 hours
of it.

**Simple verbs are confirmed on the Y-series** once the state cleared: `start` twice user-observed,
`pause`, and `dock`. Plain shape, `initiator: "localApp"`, no map id, no regions.

## And there is no whole-house shape on the routine path

@Echovictor37 tested `clean_all=True` with a valid map id, both with `regions` omitted and with an
empty list: PUBACK, nothing, twice. `CommandDTO` has thirteen fields and `select_all` is not among
them — iRobot's own code strips it before sending, so the robot never sees the key.

A whole-house clean is `send_simple_command("start")`. The field is documented as inert rather than
removed, so nobody spends another hardware session on it.

He also found that `initiator` is **mandatory but not inspected** for region cleans: `"localApp"`
behaved identically to `"rmtApp"`. Worth not over-reading — iRobot's own builder defaults to
`RmtApp` rather than omitting it.

1,234 tests passing.
