# roombapy-prime 0.2.0b9

The HTTP 500 that has blocked schedule creation for four field rounds has a cause, and it is ours.

## `create_schedules` was missing a level of nesting

The endpoint answered `AspenError.InternalError` on every attempt, with no field named and no
validation message. Three candidates were ruled out along the way — `initiator`, which the tester's
own working schedules do not carry; `is_smart_clean_fav`, which does not exist anywhere in the
iRobot app; and `created_time`, dropped in b8 and still 500.

APK analysis settled the rest. `CreateSchedulesRequest.getHttpBody()` serialises a
`ScheduleListUpdate` whose entries are `HouseholdScheduleUpdate` objects:

```json
{"schedules": [{"options": { ... }}]}
```

We were putting the `ScheduleOptions` straight into the array, so the server found `name`,
`commands` and `frequency` where it expected an object with an `options` key. A structural mismatch
like that produces a 500 rather than a 400 — which is precisely what came back, four times.

`schedule_id` is **omitted**, not sent as null. Both fields are optional with default null and this
request serialises without `encodeDefaults`, so the app skips the key entirely. An explicit null and
a missing key are not the same input to a server, and this library would have written the null.

## Why toggling always worked and creating never did

`update_schedules()` takes `HouseholdSchedule`, and `HouseholdSchedule.to_json()` already emits
`{schedule_id, options}` — the right shape, arrived at by accident of which type that signature
happens to take. `create_schedules()` takes `ScheduleOptions` and produced only the inner object.

Two paths in one module, disagreeing about a structure only one of them had confirmed. A test now
pins the update path so a future tidy-up cannot align them on the wrong shape.

## The check was printing the wrong thing

`schedule_create_delete` printed `options.to_json()` while the client wrapped it before sending. So
four rounds were spent reading a payload that never crossed the wire, in the one check whose purpose
is to show what did. It now prints the body as sent, and that is what made the missing level
visible.

## Clean score: confirmed live, and the key list was a floor

`GET /v1/p2maps/clean-score?p2map_id=<id>` works — four rooms came back and parsed exactly as
counted (@DaRealGuGu).

The real response carried three fields the confirmed key list did not have — `high_traffic_enum`,
`mission_last_cleaned`, `mission_last_unfinished` — plus `smart_clean_prefs` as a **dict** where the
Kotlin side suggested a string. All four are modelled now.

`profile` was absent, confirming the decision not to model a key another integration reads with a
fallback: its code could not distinguish "the server sends this" from "someone assumed it".

A key list confirmed from the vendor's own parser is a floor, not a ceiling. That is the argument
for printing raw responses even once a model exists.

**Open:** every room read `0.0`, with `last_updated_by` values of `batch_decay_skipped` and
`rt_mission`, so there is decay logic behind it. Whether `0.0` means spotless or unscored is not
decidable from one account whose rooms all read the same.

## `/v1/user/automations` answers

An empty array, not a 404 — so the endpoint is alive server-side even though the string is a dead
constant in the app, with one reference and no reader. A dead constant says something about the app,
not about the server.

The response structure is still unverified: that account has no automations configured.

980 tests passing.
