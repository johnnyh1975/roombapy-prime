# roombapy-prime 0.2.0b10

One crash, found by a test rather than by a robot.

## A malformed command entry took down the whole schedule parse

`ScheduleOptions.from_json()` unwrapped each command with a bare comprehension:

```python
commands=[c.get("command", c) for c in (data.get("commands") or [])]
```

A single `null` or string in that list raised `AttributeError` — from inside a parser, on a
response the server sent.

The blast radius was everything schedule-shaped. Home Assistant's schedule calendar and every
schedule switch read this, so one malformed entry would have taken all of them down together, and
the traceback would have pointed at the parser rather than at the payload.

Same shape as the `SchedulesResponse.from_json` crash fixed in b6, one level further in. Non-dict
entries are now skipped, and a `commands` value that is not a list yields nothing rather than
raising.

Found by feeding malformed shapes at the layer above, which is the only reason it turned up before a
robot did it.

## New: a read-only quiet-hours check

Quiet hours are the last unbuilt feature of the V4/Prime line, and the obstacle is not demand.
**Nobody has ever seen a populated response.** Three separate accounts return `status` empty and
every other field null, because none of those users has quiet hours set in the iRobot app.

So the model has four fields with no example behind any of them, `set_dnd_settings()`'s own
docstring admits the write body was never investigated, and the single live write attempt returned
HTTP 400 — from a check resending an empty settings object, which is what writing a shape you have
never read gets you.

`roombapy-prime-verify-writes dnd_read` sends nothing. It prints the raw response before this
project touches it, and counts the populated fields independently of the parser: a response
carrying a field the model does not know is reported as a finding rather than passing as a
configured account. That matters here more than elsewhere, because the write path resends DND
*from the parsed model* — an unmodelled field would be silently dropped on the next write.

**One person with quiet hours configured, running this once, unblocks the feature.**

## Quiet hours: the write body was wrong in three ways at once

APK analysis settled the shape, and it explains the HTTP 400 the one live attempt returned.
`DNDPutRequest` serialises a `DNDSchedule` **directly** — no envelope, no discriminator — and
`DNDSchedule` has exactly two mutually exclusive cases:

```json
{"dailyStart": 1320, "dailyEnd": 420}     quiet hours every day
{"endsAt": 1785700000}                    quiet until one moment
```

The check built its body by taking every non-empty attribute off the parsed response. So it used
the **Python** names (`daily_start`) rather than the wire keys, **mixed both cases** into one body,
and included `status`, which belongs to the response side and is not part of the write structure at
all. Three faults in one request.

The two models for these cases have existed since session 46, confirmed from the same
`$$serializer` blocks — they were never wired in because the envelope was unknown. It turns out
there is none.

The check now picks whichever case the account actually has and sends that one, built by those
models, and prints the variant and the body before sending.

### The unit is minutes since midnight

`dailyStart` and `dailyEnd` are `hour * 60 + minute`, range 0–1439 — so 22:00 is 1320 and 07:30 is
450. The formula is in the app's machine code, in the schedule-conflict check.

One caveat kept deliberately: it was read out of the *general* schedule path rather than the DND
serialisation itself. Both work on the same time-window objects, so carrying it across is
well-founded rather than proven.

`dnd_read` therefore prints each value with its clock reading beside it:

```
dailyStart = 1320  -> 22:00 if minutes since midnight
dailyEnd = 450  -> 07:30 if minutes since midnight
```

The first tester with quiet hours set confirms or refutes that by glancing at their own app. No
arithmetic, no second round — and a value outside 0–1439 says so explicitly rather than printing a
nonsense time.

`DNDDailySchedule.from_clock(22, 0, 7, 30)` does the conversion so callers do not repeat it. It
raises on an impossible time rather than clamping: a quiet period silently shifted to a different
hour is worse than a refusal, and this writes to a real robot.

Still not built into Home Assistant: no populated response has ever been seen, and the write path
should follow a read rather than precede it.

999 tests passing.
