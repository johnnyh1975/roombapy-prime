# roombapy-prime 0.5.0b1

**A beta.** The MQTT connection now runs on aiomqtt, on the event loop,
instead of paho on its own thread. `PrimeRobot` and `CloudAccount` keep
their API, and the wire does not change.

The port went through three reviews, and they found more than the port
itself: most of what they found was in how watchers get through a
dropped connection, and several of those bugs are in 0.4.0 too. The
watchers' reconnect handling is rebuilt, and tested for the first time
with the real client underneath rather than a scripted mock.

---

## Why aiomqtt

With paho, every MQTT call went to a worker thread through
`asyncio.to_thread()`, and every message came back from paho's network
thread. That meant a thread per call, a lock shared across threads, and
callbacks that ran outside the event loop. aiomqtt runs the same paho
protocol code without a thread of its own: connect, subscribe, publish
and every incoming message now happen on the event loop.

aiomqtt is also what roombapy uses, with the same version range
(`aiomqtt>=2.5,<3.0`), so the two never ask Home Assistant for
different versions.

## What stays the same

On the wire, compared to 0.4.0:
- **the same three headers** in the WebSocket handshake, the
  authorizer's, and no User-Agent;
- **the same client id**, the one the server issued, on every connection
  and reconnect;
- **the same TLS**: verified against certifi's bundle;
- **the same protocol**: MQTT 3.1.1 over WebSocket on `/mqtt`, keepalive
  60 s, QoS 1.

The errors are the same classes with the same `reason` values.

## What changes for callers

- **`PrimeRobot` and `CloudAccount`: the same methods.** They were
  coroutines already.
- **`robot.disconnect()` closes for good.** Running watchers stay and
  wait. Shadow reads, commands and subscribes raise `NOT_CONNECTED`.
  Nothing reconnects until `robot.connect()` is called again, which
  brings the watchers back. Before, the live map reconnected right after
  a disconnect.
- **Watcher callbacks run on the event loop.** A callback that blocks
  holds up every message on the connection. One that raises is logged,
  and the others still run.
- **`PrimeMqttClient`'s methods are coroutines.** The class is not
  exported from the package; code that built one itself adds `await`.
- **paho's and aiomqtt's own log lines are at DEBUG**, under
  `roombapy_prime.mqtt_client.paho`. aiomqtt switches paho's logging on,
  which 0.4.0 never did, and paho logs every connection reset at ERROR.
  This library reports drops itself, with the broker's reason.

## How watchers get through a drop now

- **Each watcher remembers the connection it watches.** A drop is "that
  connection has ended", which stays true however late the watcher
  looks. Before, a watcher only heard of a drop that happened while it
  was waiting, and it is not always waiting.
- **One watcher at a time rebuilds the connection.** The others resume
  on the connection it built, or on one a shadow read or command built.
  A fresh login happens only when the token is due, and only once.
- **A drop is logged once**, however many watchers notice it, and the
  recovery ("MQTT reconnected, watch resumed") once. Our own token
  refresh is not logged as a drop.
- **Subscriptions still unacknowledged a second after a reconnect** get
  at most two more reconnects, then the watch resumes regardless: some
  sessions deliver without a visible SUBACK.

## Fixed

Marked *(0.4.x)*: in 0.4.0 as well.

**Watchers across drops**
- **A watcher could go silent for good** *(0.4.x)*. A drop while the
  consumer was handling a message, within the second after a reconnect
  (the eviction pattern), or right behind a message was missed. The
  watcher then waited on a dead connection while the log said "watch
  resumed".
- **With several watchers, only one heard of a drop** *(0.4.x)*.
- **One drop made one WARNING per watcher** and was counted once per
  watcher. With Home Assistant's three watchers every ordinary drop set
  off the "3 disconnections in five minutes" warning.
- **Unacknowledged subscriptions after a reconnect.** In 0.4.x they were
  never retried. The first fix had no bound, and on sessions that never
  show a SUBACK it reconnected every minute while the watcher delivered
  nothing.
- **A due token meant one login per watcher.** Each token swap tore down
  the connection the previous one had built.
- **A watcher in its backoff tore down a connection a shadow read had
  just rebuilt**, and the read failed. Its backoff now also ends as soon
  as the connection is back.
- **A watcher could receive every message twice** after reconnects
  *(0.4.x)*, and then never released its topic.
- **A subscribe that overlapped a reconnect** never reached the new
  connection *(0.4.x)*.
- **A cancel of a watcher could be swallowed** *(0.4.x)*.

**Connection lifecycle**
- **`robot.disconnect()` could be undone** *(0.4.x)*. The live map
  reconnected at once, a watcher in its backoff a moment later, and a
  reconnect or `connect()` still in progress finished after the
  disconnect. Each left a connection nobody owned, under the robot's
  client id: on Home Assistant stop and on unload.
- **A cancelled connect kept its handshake running.** aiomqtt's connect
  runs in a worker thread that a cancel does not stop. The handshake is
  now waited for and closed before the next connect and before
  `disconnect()` returns.
- **A reconnect that failed or was cancelled after its own disconnect**
  left the watchers waiting.
- **The token refresh loop** could log in as fast as the server answered
  on a token that was due at once. It refreshed again right after a
  watcher had, and survived a `disconnect()` that raced `connect()`
  *(0.4.x)*.
- **A drop could be taken for a planned one** *(0.4.x)*.
- **Shadow reads could time out for good** after a drop during their
  SUBACK wait *(0.4.x)*.
- **Smaller fixes:**
  - A missing CONNACK is a `TIMEOUT` again, as with paho.
  - `disconnect()` no longer raises a cancel it did not receive.
  - A subscribe whose caller was cancelled no longer makes aiomqtt log
    the late SUBACK as an error.

## Tested

- **Unit tests:** 1340 library tests on Python 3.11 to 3.14 and 526 for
  the tools; mypy strict and ruff are clean. Each fix above was checked
  by reverting it: its test fails without it.
- **Real client and robot together:** `tests/test_watch_reconnect.py`
  runs the real client and the real robot over a fake transport. It
  covers drops, evictions, token swaps, closes, cancels and missing
  SUBACKs. The watcher tests before it used a scripted mock client, and
  they passed with every bug above present.
- **Local broker:** an amqtt broker over WebSocket with TLS. Checked:
  - the handshake sends exactly the three authorizer headers on
    `/mqtt`;
  - shadow reads, watchers, and commands confirmed by PUBACK;
  - a broker restart that the robot's watchers recover from on their own
    in under a second;
  - a token swap that is not reported as a drop;
  - a `disconnect()` that stays closed;
  - an untrusted certificate (`ShadowSSLError`,
    `ssl_local_trust_store`).
- **The integration:** ha_roomba_plus 4.3 (dev) passes its 8650 tests
  against this build, with no change to the integration.

**Known, from aiomqtt:**
- When a reconnect's handshake fails after its socket was opened, asyncio
  can log `Exception in callback ... add_writer() ... Bad file
  descriptor` at ERROR. It is harmless; the next attempt follows.
- If Home Assistant shuts down during a connect, asyncio can log a
  `CancelledError` from inside paho once.

**Not tried yet: a real iRobot account.** That is what this beta is for.
`roombapy-prime-validate` connects, reads the shadows and watches the
robot for a few seconds, all read-only; its output is the most useful
report. Drops and reconnects show up best in a Home Assistant log over a
day: one "dropped" line and one "watch resumed" line per drop.
