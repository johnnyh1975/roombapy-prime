# roombapy-prime 0.3.0b5

No breaking changes. Safe to upgrade from b4 without re-checking anything.

b4 shipped after reading the app 3.0.0 decode in full. b5 comes from
**measuring what had been read** rather than trusting that it had been —
and seventeen of the research package's files turned out never to have
been opened. Two of them held findings.

## One write path was sending something unusable

`reset_robot_parts()` built its body like this:

```
"parts": ["67", "72"]
```

`AssetPartResetDto` declares what belongs in that list: `part_id` **and**
`counter`. A list of bare id strings is neither a rejection nor a reset — it
is a request that cannot mean what it says, which is harder to notice than an
error.

Nobody has hit it, because nothing in the field calls this. It is fixed, and
`counters` is now an optional argument. The default of 0 is an inference: the
model names the field and does not say what a reset writes.

## `reset_robot()` was leaving the dangerous decision to the server

The endpoint has a declared body, and this sent none:

```
robot_password · synchronous · send_wipe
```

**`send_wipe` is the field that decides how consequential a reset is.** A
bodyless POST leaves that to a server default nobody here knows, which is a
worse position than choosing — and it was arrived at by not looking.

Behaviour with no arguments is deliberately unchanged. Nothing has ever called
this endpoint, and swapping one untested call for another is a poor trade on an
operation that may wipe a robot. What is new is that a caller can be explicit,
and `send_wipe=False` is the conservative choice.

## Map edits now say whether they half-worked

Both edit paths returned raw JSON, documented as a response that could not be
modelled. That was true of V3's opaque `data.value` and was applied to V1 and
V2 by mistake — the serialiser extract carries all four shapes.

`edit_map_checked()` returns a parsed result, and the distinction worth having
is **partial success**: a new map version with **no URL**. The edit applied and
the rendered map did not follow. In raw JSON that was indistinguishable from
success, so a caller would have shown a stale map and never known — or retried
an edit that had already taken.

`MapEditingError` names the robot's thirteen refusal codes, grouped by what a
caller should do:

```
NOT FOUND    someone else edited the map — re-read it
INVALID      fix the request
NOT NOW      send it again unchanged
```

Only the middle group means "you did something wrong". Treating all three alike
turns a transient refusal into a permanent failure.

`edit_map()` itself is untouched, so a first real response can still be
inspected whole.

## The dock capabilities are no longer six anonymous numbers

`dock.cap` was documented in code as "levels, not flags" with no statement of
what any level meant. Every one is named:

```
evac       DockEvacuation      notAvailable · available
pd         DockPadDrying       notSupported · basic · unheatedAir · heatedAir
pw         DockPadWashing      notSupported · supported · heated · highHeat
pwo        DockPadWetOut       notSupported · supported        (was "meaning unclear")
fr         DockFluidRefill     notAvailable · controllable · automatic
detergent  DockDetergent       notAvailable · controllable
```

**`DockFluidRefill` has three states and the middle one matters**:
`controllable` means the user can trigger a refill, `automatic` means the dock
decides. A refill button belongs only on the first.

`ScrubSupport`, `PointCleanSupport` and `MidMissionAdjustments` are named for
the same reason. `MidMissionAdjustments` is worth reading before use — its
levels are **not a ladder**: 1 and 2 say which missions allow skipping a room,
3 says what can be skipped.

## Who started the mission

`Initiator` has 25 values. This library knew two, from whichever captures
happened to contain them:

```
dockBtn · manual · schedule · alexa · siri · google · ifttt
homey · openHAB · yonomi · team · rmtApp · localApp · …
```

"Why did the robot start?" is a question people ask, and `cloud` versus
`dockBtn` versus `alexa` answers it. Nobody would have searched for an enum
called `Initiator` while reading a field documented as having two values — the
gap report found it.

## Fault scenes, and five of twelve are derivable

The same error code means different things per running task, which is why
the app resolves a fault against a SCENE rather than showing one text per
code. A stall during `padWash` is a dock problem; the same stall during
`cleanTask` is a robot problem.

The robot never sends a scene — `getFaultScene({cmStatus, command})` computes
it. This project recorded the conditions as "not written down"; they are
written down, as code and as a data file nobody had opened. Five are now
derivable through `FaultScene.scene_for()`:

```
evacTask   command or cycle or phase == evac
washTask   command washpad  or phase padWash
dryTask    command drypad   or phase padDry
frTask     command flrefill or phase refill
dockTask   command dock     or cycle dock
```

The dock rules match on command **or** phase: a fault during a wash is a wash
fault whether the user asked for it or the robot started it. The other seven
have no stated condition and return `None` rather than falling back to the
documented default — a plausible wrong task name on a real error message is
worse than none.

## Smaller vocabularies, and one name collision

- **`MopInstallDetails`** — four states, not on and off. `onlyLeft` and
  `onlyRight` mean ONE of two pads is fitted, which only makes sense on a
  robot with DualClean Mop Pads. A different question from `PadCategory`:
  that one says WHAT is fitted, this says HOW MANY mounting points are
  occupied.
- **`MapVerifyResult`** — a sixth client-side check, numeric where the other
  six are strings. `overlapWithVirtual` names something they do not: overlap
  with a virtual wall specifically.
- **`MapEditStatus`** — success, fail, **cancel**. Named `MapEditStatus`
  rather than the vendor's `MapEditResult`, because this module already has a
  class by that name meaning the whole parsed response. Two things under one
  name in one module is what `PadCategory` cost months.
- **`MissionType`** (`full_home` / `room_cleaning` / `zone_cleaning`) and
  **`TimelineEventPhase`** — both state outright what this library
  reconstructs. A room clean and a zone clean both arrive as `start` with
  regions; only the region types tell them apart.

## A third numbering for room type

Whether the read side reports room type as the edit codes or as strings was
recorded as unresolved. It is neither:

```
2100-2120   what SetRoomType writes
0-8         the SDK's map data model     <- RoomTypeValue, new here
strings     what the GeoJSON bundle carries
```

Nine categories, three encodings, and confusing them is silent both ways — a
`1` looked up in the write space finds nothing, and an edit built from the
small space writes 1 where 2101 was meant. `RoomTypeSourceValue` is the same
story one field over.

## The DND write shape is one step less certain than it read

`set_dnd_settings()`'s docstring says the body format is confirmed, and it
was — in APK 2.2.4. A structural diff against 3.0.0 lists
`DNDSchedule$DailySchedule` and `DNDSchedule$EndsAt` under `only_224`, and
neither appears among 3.0.0's serialisable classes.

That says less than it looks: what a client stops shipping is a fact about
that client, and this library holds the counter-example — a schedule field
arrived on real data while appearing nowhere in 2.2.4. But the confidence
behind the body shape is now "confirmed in 2.2.4, absent in 3.0.0, never sent
successfully by anyone", and the docstring says so.

## A new field check: does the server validate `initiator`?

`verify-writes custom_initiator` sends `find` — the robot chirps and nothing
else changes — claiming to be `homeassistant` rather than `localApp`.

`Initiator` lists ten named third parties including **openHAB and homey**,
home-automation platforms exactly like this one. `homeassistant` is not among
them. Either iRobot never registered it, or the field is a free string the
server passes through, and the difference decides whether an integration can
identify itself in a robot's own mission history.

It needs two observations, and one alone proves nothing: does the robot
chirp, and does the mission history afterwards name Home Assistant? A broker
acknowledgement is neither — it says the publish left the machine.

`--initiator` is overridable, so a rejection can be followed by the same run
with `openHAB` to tell "iRobot does not know us" from "iRobot does not check".

## Two things that were never gaps

**`nsmip*` and `svcEndpoints*`.** Twelve registry names were carried as
unresolvable, with what `nsmip` stands for called an open question. The
suffixes are the shadow list — `nsmipThing`, `nsmipSettings`,
`svcEndpointsCurrentState`. A flat registry needs distinct names for one key on
different shadows. A real dump confirms it exactly: bare `nsmip` on seven of
nine shadows, absent from precisely the three with no registry entry.

Both keys had been read all along. The names were looked at and the shadows
were not.

**`poll_echo_value()`.** Its body was recorded as unknown. The endpoint is
field-disproven twice over — it does not chime the robot, and neither does the
shadow write that was tried after it. `send_simple_command("find")` is the
working locate. The unknown body belongs to a call that does not do what it is
named for.

## Encodings that look alike and are not

Three concepts carry more than one numbering, and confusing them is silent both
ways:

```
room type          2100-2120 (write) · 0-8 (SDK map model) · strings (bundle)
room type source   DETECTED/USER_SET (placeholder) · user=0/robot=1 (confirmed)
routine type       FIRST_RUN… (sent) · 0-5 (SDK ordinal)
```

A `1` looked up in the write space finds nothing; an edit built from the small
space writes 1 where 2101 was meant.

The fourth was caught by a real capture rather than a second enum:
**`langs2.sLang` carries BCP-47** (`"en-US"`), not `DeviceLanguageType`'s
numeric ids. A language selector built from the vendor enum would have written
`2`. The option set is `dLangs`, which the robot supplies per device.

## Tooling, because reading was not enough

b4 was written after reading the decode in full. Two of its six new controls
were still built from recall — one shipped saying no vendor enum existed for a
value set that was in the extract, another with labels the vendor spells
differently.

So the extract now ships with the library and the checking is automatic:

- **`check_vendor_value_sets.py`** — every value set either matches a declared
  vendor enum or states why none exists. The second question is the one that
  matters: an undeclared set fails, and "I searched for the field name" is not
  a reason. The vendor names enums by concept (`padDryDur` → `DryDurType`).
- **`vendor_gap_report.py`** — what the vendor knows and this library does not
  use, across enums, serialiser classes and SDK models. Every entry needs a
  disposition; "not relevant" is valid, unreviewed is not.

The guard has already earned itself: it rejected two "exact matches" that would
otherwise have been declared confirmed, because both vendor enums carry empty
wire-value maps.

## Two questions for anyone with the hardware

Neither existed when b4 shipped.

**Which phase does a combo robot report while washing MID-mission?** A robot
with `pwReturn = 2` washes its pad during cleaning, not only at the end. The
integration's phase handling has a gap exactly there, and this is the one
observation that closes it.

**Does anyone have a dock with a fresh-water tank?** A raw shadow dump from one
would settle `fr`, `detergent`, `pwHeat`, `gwTankLvl` and the heat-level gate in
a single run. Every dock seen so far reports `pw: 1` — washing without heat.

## Upgrading

```
pip install --upgrade "roombapy-prime@git+https://github.com/johnnyh1975/roombapy-prime.git@v0.3.0b5"
```

Roomba+ v4.0.0a33 pins b4 and is unaffected — nothing in this release changes
an existing signature or value.
