# v0.1.11a22

The diagnostic tooling release. Almost everything here exists to answer one question that has
resisted six sessions of analysis: **why do region-based cleaning commands have no effect, while
producing no error anywhere we look?**

Two real bugs found this session meant we could not have seen an answer even if it had been
right in front of us — both are fixed. On top of that, several new checks now distinguish
between causes that previously all looked identical.

## 🐛 Fixed

- **A rejected MQTT subscription was recorded as successful.** `_on_subscribe()` received the
  broker's SUBACK reason code for every subscribe call this library has ever made, and never
  checked it. A subscription actively denied by AWS IoT policy (MQTT's own `0x80` failure code)
  looked exactly like a successful one. New `SubscriptionRejectedError` names the denied topic.

- **Watch-task exceptions vanished without trace.** `asyncio.gather(..., return_exceptions=True)`
  captured them into a return value that was never inspected. A real failure and a genuinely quiet
  topic were indistinguishable.

  Together these two meant a field result we had treated as evidence — the robot reacting to an
  app-triggered clean while our own wildcard watch saw nothing — may have been a broken
  instrument rather than a finding.

- **The displayed payload was not the payload sent.** `time` is added by `publish_cmd_payload()`
  after the preview is printed. This directly caused a careful analysis pass to conclude the field
  was missing when it was on the wire all along.

- **`RegionType.TID` used `"tid"` instead of the confirmed `"furniture"`.**

## ✨ Added

- **Mission-status readout around every send.** A readiness-based start refusal surfaces in
  `cleanMissionStatus.not_ready`/`.cond_not_ready` — not on `rejected/report`, not in any error
  field. We modelled those fields long ago and never read them during a test. Codes are named via
  a new (deliberately partial) `RobotReadinessState`; unknown values stay `UNKNOWN_<n>` rather
  than getting a guessed label.

- **Three pre-flight checks, none of which move the robot:** stale map version in the favorite,
  mopping mode requested without a pad fitted, and a round-trip fidelity check comparing the raw
  stored favorite against what we actually re-serialize — any field our models don't know is
  silently dropped, which would produce a command subtly less complete than the app's.

- **Every diagnostic script now ends with a complete report** instead of a bare count.

- **`PolicyZoneFeature.category`**, plus `PadCategory`, `MissionCommandType.POINT_CLEAN`,
  `raas`/`odoaLite`.

## What a test run can now distinguish

Where previously every outcome looked like "nothing happened", a single session run now separates:
subscription denied · command not delivered · delivered but refused for a named readiness reason ·
stale map version · pad/mode mismatch · fields dropped in our own round-trip · genuinely accepted
and ignored.

588 tests passing, ruff clean.
