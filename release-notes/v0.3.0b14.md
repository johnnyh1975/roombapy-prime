# roombapy-prime 0.3.0b14

One tool fix, from a report that took two rounds to understand — and the
second round only happened because @chairstacker noticed something that
contradicted what the tool told him.

## Zone names: the tool was looking in one of three drawers

`--list-rooms` reported "no zone names in the map bundle" on a map that
demonstrably had them. It read the `cleanZones` layer and nothing else.

@chairstacker's bundle contained five files — borders, manifest,
metadata, **policyZones**, rooms — and no `cleanZones` at all. Bundle
contents vary per map: one with only keep-out zones has policyZones,
one with ad-hoc zones has a third layer again.

So the message was true about the search and wrong about the data. He
then noticed the same names appearing in calendar entries, which is
what made it obvious.

All three layers are read now. A keep-out or no-mop zone is marked with
its `zone_type`, because sending a cleaning command at one is the
mistake worth preventing; a clean zone is left with its plain name.

And the message no longer claims more than it knows — it names the
layers it searched rather than asserting the names exist nowhere
readable.

## Also

- **`condNotReady` codes are named after all.** A comment here claimed
  their meanings were unknown and would need control-flow disassembly.
  `RobotReadinessState` names them in the file next door: 75 is
  `NO_VAC_WITH_PAD`, 22 is `MAP_VERSION_MISMATCH`, and a real robot
  reported 234. The values stay plain ints so an unrecognised code
  reaches the caller instead of raising; callers wrap them with
  `name_for()` when they want a name.
