# roombapy-prime 0.5.0

The first stable release of the 0.5 line, and the one ha_roomba_plus
4.3 is built on. Its code is 0.5.0b2's, unchanged. Coming from 0.4.0,
this is what is new; the details are in the [0.5.0b1](v0.5.0b1.md) and
[b2](v0.5.0b2.md) notes.

## The MQTT connection runs on the event loop

- **aiomqtt instead of paho on its own thread.** Connect, subscribe,
  publish and every incoming message happen on the event loop. No thread
  is started, and nothing is handed to a worker thread per call.
- **The wire is unchanged:** the same three authorizer headers and no
  others, the client id the server issued, TLS verified against
  certifi's bundle, MQTT 3.1.1 over WebSocket.
- **The same version range as roombapy** (`aiomqtt>=2.5,<3.0`), so the
  two never ask Home Assistant for different versions.

## Watchers get through a dropped connection

The watcher reconnect handling is rebuilt. Several of the bugs it fixes
are in 0.4.0 too:
- a watcher could go silent for good after a drop while the log said
  "watch resumed";
- with several watchers, only one heard of a drop;
- a watcher could receive every message twice after reconnects;
- a subscribe overlapping a reconnect never reached the new connection.

Now each watcher remembers the connection it watches, one watcher at a
time rebuilds it, a due token means one login rather than one per
watcher, and a drop is logged once.

## `disconnect()` closes for good

Running watchers stay and wait; shadow reads, commands and subscribes
raise `NOT_CONNECTED`; nothing reconnects until `connect()` is called
again. In 0.4.0 the live map could reconnect right after a disconnect,
leaving a connection nobody owned under the robot's client id.

## One login for every Prime robot of an account

`CloudAccount.prime_robot(blid, auto_refresh=True)` renews the robot's
MQTT token through the account. Robots whose tokens fall due together
log in once, and a robot takes a fresh login another one has just made.
A failed login answers for 30 seconds instead of being retried, so
robots on their own schedules cannot keep a locked account locked.

## For callers

- **`PrimeRobot` and `CloudAccount` keep their API.**
- **Watcher callbacks run on the event loop.** A callback that blocks
  holds up every message on the connection; one that raises is logged
  and the others still run.
- **`PrimeMqttClient`'s methods are coroutines.** The class is not
  exported; only code that built one itself has to add `await`.
- `PrimeFactory.create_prime_robot()` takes a `relogin` callback.
- paho's and aiomqtt's own log lines are at DEBUG, under
  `roombapy_prime.mqtt_client.paho`.

## Tested

- 1347 library tests on Python 3.11 to 3.14 and 526 for the tools; mypy
  strict and ruff are clean.
- The watcher tests run the real client and robot over a fake transport;
  a local broker over WebSocket with TLS covered the handshake, a broker
  restart, a token swap and a `disconnect()` that stays closed.
- ha_roomba_plus 4.3.0b6 to 4.3.0b10 have been built on 0.5.0b2 since
  1 October.

## Known, from aiomqtt

- When a reconnect's handshake fails after its socket was opened,
  asyncio can log `Exception in callback ... add_writer() ... Bad file
  descriptor` at ERROR. It is harmless; the next attempt follows.
- If Home Assistant shuts down during a connect, asyncio can log a
  `CancelledError` from inside paho once.

## For the command-line tools

`pip install roombapy-prime-tools` installs 0.5.0 without `--pre`.
