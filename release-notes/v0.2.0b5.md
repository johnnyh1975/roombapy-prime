# roombapy-prime 0.2.0b5

The check added in b4 could not have worked on any account. It has now been fixed, tested, and made
to show its own working.

## `verify-writes schedules` reported "0 households" for everyone

The check read three values with `getattr()`. All three are plain dictionaries:

- `get_user_households()` returns raw JSON, not a typed object
- each household inside it is a `dict`
- each schedule is a `dict` — `SchedulesList.schedules` is `list[dict]`, as its own docstring says

`getattr()` on a dictionary returns the default. So the check reported `0 household(s) on this
account`, never called `get_schedules()` at all, and reported that as a passing check — on every
account in existence, regardless of what the server would have sent.

A tester with three schedules visible in his app produced output byte-identical to what a working
account produces. That was the second field round in a row to end with no information.

The three bugs were independent: fixing only the first would have produced the same empty answer at
the second, then the third.

There was no test on this function.

## The output now shows the server's own answer first

A parsed count cannot distinguish "the server sent nothing" from "we failed to read what it sent",
and that ambiguity is what cost the two rounds. So the check now prints, in order:

1. the **raw** `get_user_households()` response
2. the **raw** `get_schedules()` response, per household
3. the parsed reading of each, as a cross-check

When the raw response contains schedules and the parser reads none, the check says so directly —
`DISAGREEMENT: the parser is wrong, not the account` — instead of leaving a zero to be interpreted.
When the household response is non-empty but unreadable, it names that as a parsing gap in the tool
rather than reporting an empty account.

`owner_cognito_id` and `household_users` are masked before printing. `household_id` and
`household_robots[].robot_id` are not: which household holds which robot is the open question on a
mixed Classic/Prime account, and masking those would remove the answer along with the risk.

## Finding nothing is no longer a passing check

A run that produced no evidence either way now reports `SKIPPED` with the reason, not `✓`. The final
summary counts it separately.

## New: `get_schedules_raw()`

`get_schedules()` returns a parsed `SchedulesResponse`, which has already dropped anything this
project does not model — so it cannot be used to find out whether this project is dropping something.
`get_schedules_raw()` returns the unparsed response. Diagnostic use only; the normal path is
unchanged.

Present on both `PrimeRestClient` and `PrimeRobot`, and added to the wrapper signature guard. A
method added to the client alone raises `TypeError` before any request leaves the machine — that is
what a28 cost.

## Household shapes

`_list_schedules` now accepts exactly the shapes `PrimeRobot.get_household_id()` accepts: a bare
list, or a single household as a top-level dict. No guessing at wrapper key names — a plausible guess
that silently returns an empty list is the bug being fixed here.

920 tests passing.
