# roombapy-prime 0.3.0

First stable release of the 0.3 line.

Eighteen betas. The core — login, MQTT, region commands, map editing,
schedules — has been stable and field-confirmed for weeks. The last six
were about one question.

## Where zone names live

Four releases reported "no zone names found in the bundle" after a
search that had not happened:

| | |
|---|---|
| **b13–b14** | widened a search that was not running — `zone_layers` read with `getattr` on a dict, so every bundle returned `{}` |
| **b15** | fixed that reader, which the call never reached |
| **b16** | fixed the call — the geojson link is a dict, not a URL |
| **b17** | fixed what the call then hit — `parse_map_bundle` is a module function, not a robot method |

Each fix was correct. Each was one layer above a fault nobody had
looked for, because the failure looked the same from outside every
time.

**The answer depends on the layer.** `cleanZones` carries names —
confirmed on a G185020 with nine read. `policyZones` has no name field
at all: a raw dump from a Y351020 shows a FeatureCollection whose
properties carry only `{"type": "NoMopZone"}`. The app does not offer
naming for keep-out and no-mop zones, and the bundle agrees.

So "stored somewhere this tool does not yet read" was wrong, and "they
are always there" would have been equally wrong.

## The tests that let it happen

Every bundle test mocked `parse_map_bundle` **as a robot method** — an
attribute `PrimeRobot` does not have. The mocks agreed with a call site
that could only ever raise, and two bugs shipped green behind them.
Fourteen tests failed when they were switched to a real tar.gz through
the real parser.

b15's own release notes had named that exact failure mode for a
different fixture, one function down.

## Also in this release

- **`current_map_version`** resolves whichever field a robot uses to
  name its current map version. Some send `active_p2mapv_id`, some send
  `user_p2mapv_id` and `p2mapv_id` and no `active_` field at all — and
  a request without a version returns whatever the server defaults to.
- **Absence and failure are different findings.** A bundle read that
  throws now says the question is unanswered by that run, rather than
  printing the same "no names found" conclusion as a search that
  completed.
- **The room listing shows regions the snapshot does not know**, in
  both directions — created zones the snapshot has not caught up with,
  and deleted ones it has not dropped.
