```
All shapes were sent and all were rejected.
```

The a28 attempt reported the same conclusion while nothing had left the machine. This one is real,
and `response_type` is out.

## The wall format is confirmed, and was already correct

A second, independent read of the app's custom `VirtualWall` serializer settled every open detail:

- Type codes `1` (keep-out), `6` (no-mop) and -- new -- **`2` for linear walls**, which no tester
  has configured and nothing had corroborated.
- A linear wall is encoded as a **degenerate quadrilateral** (`from -> to -> to -> from`) so a
  two-point line fits the same fixed 10-element schema as the area types.
- Only `coordinates[0]`; interior rings are ignored.

Every one of these already matched, and a real field payload matches element for element. That is
a negative result for the HTTP 500 hunt, and a useful one: the wall array is not the problem.

### One real bug did surface

The app takes **exactly the first four points**. This library dropped the closing point only when
the ring was closed -- identical output for a rectangle, which is why field payloads looked right.
A five-point open polygon produced 12 elements against the app's 10.

## `set_virtual_wall` replaces the entire list

From the same read: every write in the app fetches the latest map, extracts keep-out zones, no-mop
zones **and** virtual walls, and sends the combined list. All three share one `virwall` array.

So sending only the wall you want to add deletes everything else on the map -- silently, with no
error and no undo. Documented, with a guard test.

Not the explanation for the 500: the verify script's `--update-unchanged` already reads the full
list and resends it untouched.
