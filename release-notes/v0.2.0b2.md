# roombapy-prime 0.2.0b2

Field-driven fixes to the write-verification tooling, plus findings from APK analysis and four
testers' captures.

## The tooling was producing false failures

Two checks reported endpoint failures that were the checks' own fault.

**Quiet hours returned HTTP 400** because the check resent an empty settings object on an account
with no quiet hours configured. The server was right to refuse it.

**Schedule creation returned HTTP 500** because the check built a schedule from a name and nothing
else — no robot, no days, no time, no commands.

Both were reported as "this endpoint does not work". Both endpoints were fine.

The rule now: **a check derives its payload, never invents one.** It reads the current value and
sends it back, changed minimally or not at all. Nothing to read means the check skips and says why.
A robot with no schedules cannot test schedule creation, and that is an honest result rather than a
reason to guess.

**And a crash of ours masked both.** `report.add(..., "FAIL", ...)` raised `KeyError` — the status
must be `"FAILED"` — so a check that failed cleanly with an HTTP error turned into a traceback, and
the summary crashed on the way out. Two of a tester's runs ended that way.

## Confirmed by real captures

**`padWetness` spelling.** A real `rw-settings` capture reads
`{"disposable": 3, "reusable": 1, "padPlate": 1}` — camelCase, as the command-domain model assumed.
That had been the last blocker for a pad-wetness control.

**But the value range belongs to neither known enum.** `RobotPadWetnessLevel` runs 0–2 with 3 as
invalid; the app's own `PadSettings` runs 0–2 as LOW/MEDIUM/HIGH. A working robot reported 3. The
obvious guess — 1-based counting of a known enum — does not hold either. The wire uses a third scale
nobody has identified, and a control must not assume one.

**`get_time_estimates` response.** Never seen before. It returns one estimate per room **per
parameter combination**, not one per room — a single room came back with dozens of entries covering
every mix of operating mode, suction level, scrub and two-pass. So it answers "how long would this
room take at these settings".

**Schedule fields.** All sixteen match the app's own `ScheduleOptions`, and every field is nullable
in Kotlin — the server decides what a valid schedule needs. There is no client-side validation to
add.

## Dock commands

Three confirmed wire strings from `CommandType`'s `@SerialName` annotations, the same source as
`find`:

    Empty Bin              evac
    Wash mop / rinse dock  washpad
    Stop mop dry           stoppaddry

`drypad`, `flushsluice`, `flrefill` and `querydock` exist in the same enum. `evac`/`stopevac` and
`drypad`/`stoppaddry` come in pairs; there is no `stopwashpad`, so washing runs to completion.

## Documentation

Map orientation is in **radians** — `1.5708` is a quarter turn. The help text never said, and `90`
would have rotated a map about fourteen times.

907 tests passing.
