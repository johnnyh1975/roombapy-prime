# roombapy-prime 0.3.0b18

The last beta before 0.3.0, and it fixes a question that cost a tester
four hardware runs.

## Asking for the current map version, and not getting one

`active_p2mapv_id` comes from the vendor class's own field list, and
some robots simply do not send it. @chairstacker's G185020 reports
`p2mapv_id` and `user_p2mapv_id` instead.

So a caller asking for "the current version" got None, the bundle
request went out without one, and the server returned whatever it
defaults to. A zone he created that morning was missing from a bundle
read that afternoon — while the version carrying it sat in the same
response.

He tried four ways to bring it in: renaming a room, creating a zone,
renaming a room again. All four had to fail, because the request never
carried a version. That was our bug, and I told him it was the cloud
lagging.

`current_map_version` resolves whichever field the robot uses.
`user_p2mapv_id` wins: it is the version the user's own edits produced.

## A docstring that argued with itself

One paragraph recorded @Echovictor37 firing `clean_all` on hardware —
`regions` omitted and `regions` empty, PUBACK both times, no effect
either time. Another, further down, said "STILL UNTESTED".

The wrong one got read, and it sent @BryznNguyen offering to spend a
hardware run on a question that had been answered months earlier.

Fixed. What remains open is narrower: whether a whole-house clean
*through that path* would need the same START-not-CLEAN treatment a
region clean does. It cannot be answered by sending `clean_all`,
because iRobot's own client strips the key before sending.
