# roombapy-prime 0.7.1

**Why a login can return no robots, said from the login itself, and the
Combo j7+/j9+ recognised as Classic.**

## The login's ownership fields

`/v2/login` can name robots that belong to **another account**. The
Classic app 7.18.0 reads two fields for that from the answer,
`conflicted_robots` (a list of robot ids) and `conflicted_user_count`
(how many accounts), and offers to take the robots over. This library
dropped both. A robot registered to someone else's account -- a
second-hand robot, as in #93 -- made the login return no robots, and
nothing said why.

- `LoginResult.conflicted_robots` (`tuple[str, ...]`),
  `LoginResult.conflicted_user_count` (`int | None`) and
  `LoginResult.has_ownership_conflict()`.
- The `no_robots` error and the "authenticated" log line add the
  conflict **by count**. Robot ids stay out of messages that end up in
  issues.
- Optional fields: a missing or odd value is "no conflict reported",
  never a failed login.
- Nothing is taken over. The library sends `assume_robot_ownership:
  "0"`, as the Classic app does until its user confirms.

The fields have not been seen on a real answer yet; the first account
with the problem will show whether the server fills them.

## The Combo j7+ and j9+ are Classic

Their SKUs start with `c` -- `c755020` (Combo j7+), `c975860` (Combo
j9+) -- not with `j`, and the Classic table had no `C7` or `C9`. So
`sku_generation()` said `"unknown"`, and ha_roomba_plus, which sends an
unknown SKU down the Prime path because new models are Prime, set a
Combo j9+ up as a cloud-only robot. It runs on the Classic local
connection, and the reporter's robot cleans rooms that way.

Both prefixes are in `CLASSIC_SKU_PREFIXES` now, from real devices.
Matching is on two characters, so they cover each family's variants.
No Prime prefix starts with `C`, and the import-time overlap check
would stop one that did.

## The Prime app's device list

`get_associated_robots_raw()`, on every REST client and on
`CloudAccount`, reads `GET /v1/user/associations/robots`. The Prime app
3.2.0 takes its device list from there, not from the login. A login
with no robots is therefore not proof that the account has none, and
this call tells the two apart.

- Read only and unparsed: the answer's shape is not known yet.
  `count_associated_robots()` counts it and returns `None`, not 0, for
  a shape it does not recognise.
- A robot listed only there has no deployment and no password from the
  login, so it cannot be connected. The call explains; it does not
  replace the login's list.
- Host and signing follow the app's parts call (`http_base_auth`,
  SigV4). Not yet called live.
