# v0.1.11a29

a28 shipped broken. This fixes it, and adds the guard that would have caught it.

## The virtual-wall experiment never ran

a28 added a `response_type` parameter to the REST client and not to the wrapper the scripts
actually call. All three request variants died with `TypeError` before anything left the machine.

Worse than a wasted run: the script then announced that `response_type` had been ruled out as the
cause. Nothing had been tested. A tester spent an evening producing one confidently wrong
conclusion.

That is the same failure mode as reporting a missing delivery confirmation as a server-side block —
a local crash presented as evidence about someone else's system. The script now says outright
**"NOTHING WAS ACTUALLY SENT — this run rules out nothing at all"** when a request never reached
the network, and only genuine responses count.

A guard test now compares the wrapper's signatures against the REST client's. A wrapper that cannot
forward an argument is trivially detectable and expensive to miss; this one cost a full round trip
to find.

## System uptime is powered-on hours

Confirmed by two accounts at opposite ends of the range — one robot rarely switched off showed a
14-hour gap against wall-clock time, another unplugged for months showed 5579 hours. Both match
what their owners recalled, and if this tracked wall-clock time both gaps would have to be near
zero.

Worth stating for anyone building on it: **this is not device age.** On a robot that has spent
months unplugged the two differ by more than half.

## Robot generations can now be told apart properly

`is_prime_sku()` answers one question: is this Prime? It has never been able to answer the
other — is this Classic? — and returning False for both a Classic robot and an unrecognised one
conflates two very different situations.

Three additions close that:

- **`is_classic_sku()`** and **`sku_generation()`**, the latter returning `"prime"`, `"classic"`,
  `"dock"` or `"unknown"` — where **unknown is a real answer**, not a fallback.
- **The Classic side of the SKU table**, 20 prefixes covering a closed generation.
- **`W15` (EnhancedMaxVac)**, which was missing from the Prime table.

### Two characters, and both bounds matter

One is too few: SkuUtils.java uses `R` for both generations — R285020 is Prime, R980020 is
Classic, and one tester's account holds exactly that pair.

Three is too many, and that took field data to see. The APK table lists one default SKU per
internal platform, not the variants actually sold. At three characters, **four of five Classic
field robots fall outside it** — i755840 against the table's i71, i355640 against i31. At two they
all match, and the Prime and Classic sets stay disjoint. An import-time check fails loudly if a
future SKU ever breaks that.

Eight product families absent from the APK were added from the shipped range (i4, i5, i6, i8, j5,
j6, e5, e6). One candidate was **deliberately dropped**: iRobot sold a Classic "q" series, but
Prime's CongoVacuum is Q012020, so `Q0` belongs to Prime. Claiming it for Classic would have routed
a cloud-only robot down the local path — which is why every addition is checked against the Prime
set first.

## Documentation brought in line with reality

Three claims in the docs were flatly false by the time anyone read them:

- The package described itself as *"Draft, unverified against real V4 hardware"*. Dozens of paths
  are confirmed across three independent accounts.
- The README called region cleaning *"the one significant thing that does not work yet"*. It has
  worked since a26, both from a saved favorite and built from scratch.
- The tools listed virtual-wall and settings writes as *"never run by anyone yet"*. Both have been
  run repeatedly, with very different outcomes — settings work, virtual walls return HTTP 500.

Also rewritten: the internal write-path status page (it was still describing region commands as
the central blocker), and the API reference, which listed region commands as *"experimental,
unconfirmed, NOT live-tested"*.

### One structural fix worth calling out

The API reference used 🟢 for two different claims: *"we read this out of decompiled source"* and
*"a robot actually did this"*. Those are not the same thing, and conflating them is the easiest
way to misjudge this library — virtual walls are 🟢 by derivation and return HTTP 500 in practice.

The legend now separates *how the shape was derived* from *whether it has ever been run against
hardware*, and the latter is written out rather than given a colour, so it cannot be skimmed past.
