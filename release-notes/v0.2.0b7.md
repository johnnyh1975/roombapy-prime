# roombapy-prime 0.2.0b7

Two reporting fixes, both from the same field round: @chairstacker's `schedule_create_delete` run
reached the server for the first time and came back with `HTTP 500` and nothing else.

## The server's explanation was thrown away

`RestError` has carried the response body in `raw_response` all along. The report printed
`str(exc)` — which is `HTTP 500 from <url>` and nothing more.

So a round that finally got the check running produced a status code, and whatever the server said
about *why* never left the exception object.

This is the third time in three releases that the failure was not the code doing the work but the
layer reporting on it: b5 had a check that never queried the account, b6 had a crash in the branch
meant to explain an empty result, and now a 500 with the explanation stripped off. Failures now
include the response body.

## The request body is printed before it is sent

Two candidate causes for that 500 were arguable from the source alone and not distinguishable
without the payload:

- `created_time` is copied from the template schedule and sent back — a field the server assigns
- the copied `commands` carry regions, and `initiator` is mandatory there; the app adds it at send
  time and stored schedules do not have it, which is exactly what made region cleaning look broken
  for months

Guessing between them is what this project does not do. The check now prints the exact JSON it is
about to send, so one more run answers it.

## Also in b6, confirmed in the field

`schedule_create_delete` reached the server at all. Before b6 it located its template schedule with
`getattr()` against raw dictionaries, so it always reported "this account has no schedules" and sent
nothing. @chairstacker's run shows it copying a real schedule, renaming it and posting — the fix
works; the 500 is a separate question.

The household id printed in that run is the b6 addition too.
