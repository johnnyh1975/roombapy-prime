# roombapy-prime 0.3.0b12

The local channel answered.

A field run on current firmware settled a question this project had
been guessing at, disproved one of its hypotheses, and exposed three
ways the discovery tool could have reported silence from a robot that
was talking.

```bash
pip install --upgrade "roombapy-prime-tools@git+https://github.com/johnnyh1975/roombapy-prime.git@v0.3.0b12#subdirectory=tools"
```

One command — the tools package declares the library as a dependency
and brings the matching version with it.

## The robots never dropped the local channel

This library concluded, from decompiling three app versions, that the
local path *had been removed*: app 2.2.4 carried 46 local-socket
serializers, `irobotmcs` discovery and port 5678, and app 3.0.0 has
none of it.

The app evidence was right. The conclusion overreached. **The app
stopped using it; the robots did not.**

Confirmed twice on `p25-705+9.3.6+I3.8.149`, current firmware: a field
tester's discovery run answered with port 8883 open, and an
independent implementation speaks the channel live.

What an app ships says nothing about what firmware still serves — a
distinction this project built a whole tool around, and then failed to
apply to its own notes one file away.

## Three ways discovery could have lied

All three share one failure mode: the robot answers, we fail to hear
it, and the run reports nothing found. That reads as *"the firmware
dropped the local channel"* — the exact question the tool exists to
ask.

- Some robots **prefix the discovery JSON with a 2-byte big-endian
  length**. A plain `json.loads()` throws on those, and the reply was
  discarded silently.
- **BLID now falls back to the hostname** (`iRobot-<blid>` /
  `Roomba-<blid>`) when `robotid` is absent, rather than leaving a
  robot unidentifiable with its BLID one field away.
- The discovery packet now goes to **both the subnet-directed
  broadcast and 255.255.255.255**. Some routers drop the global one.

Found by comparing against an independent implementation of the same
protocol. Any of them could have turned a working robot into a data
point that said the opposite.

## The TLS hypothesis was wrong, and the field proved it

The reasoning was: the robot's bad signature arrives in
`CertificateVerify`, a **TLS 1.3** message, so capping the connection
at 1.2 sidesteps it — no native helper needed.

A field run failed with `BAD_SIGNATURE` on **both** attempts.

The robot signs with a key that does not match the certificate it
presents. TLS 1.3 carries that signature in `CertificateVerify`; TLS
1.2 with an ECDHE suite carries it in `ServerKeyExchange`. Capping the
version changes **which message holds the bad signature, not whether
one is sent.**

A clean negative that no amount of reading could have produced.

**One case remains untested.** A static RSA suite has no server
signature at all — the client encrypts to the certificate's public key
and nothing is signed. If the robot's legacy stack offers one, the
mismatched key is never exercised. The tool now tries it as a third
attempt.

So a native helper with a patched TLS library is the only route anyone
has **got working** — not, as this project previously implied, the only
route that could exist.

## Dock reports are a real topic family

`dock/paddry/report` was filed as settled-dead on the grounds that no
report topic appears in app 2.2.4 or 3.0.0. Wrong test: a field tester
had **captured one live**, and an independent SDK log lists four.

`dock_report_topic()` now builds the family and
`PrimeRobot.watch_dock_reports()` subscribes it. With no argument it
uses a `+` wildcard — the only way to discover whether a `reportType`
other than `paddry` exists. **A `charge` or `battery` sibling would be
the real find**; none has been seen.

`DockReport` aliases `DockPadDryReport`, whose model already keyed off
`reportType` and so always fitted the whole family.

## `geojson_details` is confirmed live

Marked here as existing in no app version checked. It returns room
names on current firmware.

It lives in ARM64 native blocks, which a DEX-and-Dart search cannot
reach — a limit of the search, not of the protocol.
`parse_map_version_regions()` now has tests mirroring a real response.

The confirmed output is **rooms**. Whether the same document carries
**zones** is untested; on the one robot where zone names were chased
down they came from the bundle's `cleanZones` layer instead.

## A correction that mattered before anyone was affected

On a silent run, the local-channel tool said the robot not announcing
itself was *"the expected result on current firmware"*.

That would have misled every tester who ran it. The channel is **closed
until something opens it** — it comes up as part of the BLE
provisioning flow and closes again on reboot. Silence means "nobody has
provisioned this robot recently", not "the firmware dropped it".

A dozen "no answer" replies would have been read as confirmation of
exactly the wrong conclusion.
