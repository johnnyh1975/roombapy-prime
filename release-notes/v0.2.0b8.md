# roombapy-prime 0.2.0b8

One change to the schedule-creation check, and one long-standing question answered.

## `created_time` is no longer replayed into a create

Creating a schedule works by copying an existing one — a schedule built from a name alone got HTTP
500 from a real server, because it says nothing about which robot, which rooms or what to do.

But copying meant sending back the template's `created_time`, a field the server assigns. In
@DaRealGuGu's b7 run that was literally `2026-08-01T18:15:09.211030+00:00`, lifted from the schedule
being copied.

It is now dropped, and the check prints what it left out and why, so a run that still fails stays
readable. Three field rounds on this one check have ended with a status code and no way to see what
was actually sent.

## Why `created_time` and not the other two

b7 made the server's own answer visible for the first time:

```json
{"errorType": "AspenError.InternalError", "errorMessage": "Internal error"}
```

A crash rather than a rejection, which fits a value the server expected to assign itself. The other
two candidates were ruled out rather than set aside:

- **`initiator`** is not required. @DaRealGuGu's working, server-stored schedules carry region
  commands without it. The field is added by the app when sending a direct clean command, not when
  storing a schedule.
- **`is_smart_clean_fav`** — which the server sends and this library does not model — does not exist
  anywhere in the iRobot APK, in Kotlin or native. The server added it without its own app knowing
  about it, so its absence from a request cannot plausibly crash the server. `ScheduleOptions`
  remains complete at sixteen fields for the app as shipped.

If this run still returns 500, the payload is not the problem and the endpoint is the next question.

## Mop wetness: the impossible value was not impossible

A capture that blocked any wetness control for weeks read:

```
padWetness: {"disposable": 3, "reusable": 1, "padPlate": 1}
detectedPad: "padPlate"
```

A 3 fitted neither known scale — `RobotPadWetnessLevel` calls it Invalid, and the UI's `PadSettings`
stops at 2.

APK analysis found a second enumeration. `padPlate` has its own, offset by one:

```
RobotPadWetnessLevel:       0 Damp     1 Moderate  2 Wet       3 Invalid
RobotPadPlateWetnessLevel:  0 Invalid  1 Damp      2 Moderate  3 Wet
```

The robot has a hard pad plate fitted, so `padPlate: 1` is Damp on its own scale, and `disposable: 3`
is Invalid — no disposable pad is fitted, and the field says so. Nothing was out of range; the value
that looked wrong was in the field for a pad the robot does not carry.

`ppWetLvl` reads as a count of usable steps rather than as a flag, which also explains the robot
reporting 0 while still mopping.

Documented rather than implemented. A control still has to pick which of the three fields to write,
and `detectedPad` is what decides that — writing `padPlate` on a robot carrying a disposable pad
would apply the wrong scale to the wrong field, and the robot would accept it.

## Dock state 671, settled

A controlled before/after had already established what 671 means in the field: clean water tank
removed, `dock.pwState` reads 671; tank refitted, it reads 601 (pad wash okay), with `dock.state`,
`dock.error` and `pdState` unmoved throughout.

APK analysis now confirms the code does not exist in the app at all — the pad-wash family ends at
669, there is no second dock-state table, and `DockStateImpl` carries the fallback string
`"Unknown dock state %d"`. The official app shows nothing better than a number here either.

So the server is ahead of app version 2.2.4, the same way it sends `is_smart_clean_fav` on schedules
the app does not model. `DockState`'s docstring now says so: consumers must handle unknown values
rather than assume the enum is exhaustive.

Recorded in the same place, explicitly as a question rather than a finding: the low values 1-3 in
this enum share their numbers with the `dock.cap` flags in the shadow, which would make `dock.cap`
describe which KIND of wash and dry a dock supports rather than a bare level. That is a numeric
coincidence across two namespaces, and this project has been caught by exactly that shape twice.
Nothing is built on it.
