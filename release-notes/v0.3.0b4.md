# roombapy-prime 0.3.0b4

Required by Roomba+ **v4.0.0a33**.

A full decode of iRobot app 3.0.0 — 541 Dart enums, 89 SDK models, 223 Kotlin
serialisers — was read against this library. Four wire values were wrong, one
filter quietly discarded good data, and four robot models were not recognised
at all.

## Read this first if you compare enum values

Five breaking changes, and every one of them replaces a value that was wrong.

```
MissionCommandType   STARTDONOTDISTURB → START_DND        "start_dnd"
                     STOPDONOTDISTURB  → STOP_DND         "stop_dnd"
                     POINTCLEAN_VENDOR, FLUIDREFILL_VENDOR  removed
RegionType.TID       "furniture" → "tid"
CleaningProfileType  "DEEP" → "deep"  (and the other three)
PadCategory          mission_history's copy removed; use mission_control's
RoutineCommand       command_type may be None or str
```

The four removed command members never existed on the wire. They were constant
names read off `CommandType`, a domain enum that mirrors its own member names —
which looks exactly like a wire-value table and is not one. `mission_model
.toPayload`, the function that builds the published command body, carries all
twenty commands lowercase.

That same mistake produced `RegionType.TID = "furniture"`, the uppercase
profile types, and the duplicate `PadCategory`. One root cause, four symptoms.

## Four robot models were treated as unsupported

`U1`, `V1`, `W2` and `Z1` — the Roomba 205, 615, 715 and 875 — were missing
from the SKU prefix table, which came from app 2.2.4. `is_prime_sku()` returned
False for them.

That fails quietly by design: False means "not known to be Prime", never
"confirmed Classic". For these four it was a Classic answer in practice, and
an owner would have been set up as something they are not.

## An account with seven favourites looked like an account with none

@chairstacker has been missing his favourite buttons for weeks, across two
fixes that each looked right. Comparing the Classic and Prime paths properly
found three differences, any one of which alone produces an empty list:

| | Classic | Prime |
|---|---|---|
| what the call returns | raw dicts | typed objects |
| `commanddefs` | counted only | each command through a strict enum |
| filtering | none | id must parse, plus not-deleted, not-hidden |

**One unparseable favourite cost all of them.** Commands were built with a
strict constructor, so a single unfamiliar value raised and the exception
escaped the whole list. The caller logs at debug and returns `[]`. Each
favourite is now parsed on its own, and a failure costs that one — at warning,
with the id.

**And the diagnostic had the bug it exists to diagnose.** `get_favorites_raw()`
returned `[]` for a wrapped response, so every diagnostics download taken to
ask "did the server return anything?" answered no, whether or not it had. That
is why the previous two attempts were guesses: there was no instrument.

Not announced as fixed. Three causes, two addressed, and a download taken on
this release will say which — for the first time.

## Estimates the robot called good were thrown away

`is_confident` is a filter, not a label: a low-confidence estimate is
discarded, not shown with a caveat. It compared against `GOOD_CONFIDENCE`,
the constant name from 2.2.4. App 3.0.0 sends `good`.

Nothing had broken yet only because the live response carries no confidence
field at all. It was one server change away from silently discarding every
estimate.

## A failed subscribe poisoned the topic for the session

Thanks to **@jouwdan** (#62), who found this on a Max 705.

The callback was recorded in `_persistent` before the broker-level subscribe
was attempted. A failing subscribe left the topic registered with no
subscription — and the next attempt read "already subscribed" and skipped the
broker call. Permanently unsubscribed, permanently registered, and
indistinguishable from a robot that says nothing.

That is why his integration stayed broken across retries rather than failing
once.

One correction to the report behind it: a missing SUBACK has not been fatal
since b3 — it is recorded and warned about. The docstring still claimed
otherwise, which is how the wrong cause looked plausible. Both are fixed.

## The value sets are now checked, not remembered

Two of the six new controls in a33 were built from recall while the full
extract sat unread. `padDryDur` shipped with a comment saying no vendor enum
existed; `DryDurType` was in the extract. `pwHeat` shipped with wrong labels
and no dock gate.

Reading a document does not make its contents available at the moment of
writing code. So the extract now ships with the library as
`vendor_reference.json` — 480 enums, 35 capability gates, 24 writable
settings, 20 command wire values — and value sets declare which vendor enum
they come from. A guard checks them.

Declared, not discovered: matching by shape produces false hits. `{0, 1, 2}`
"exactly matches" four different vendor enums. A match is only evidence when
the name came first.

## Also in this release

- **Six timeline status enums.** `RoomStatus` scored the project's own
  guesswork: 6 was correctly inferred as "aborted in room", 5 was inferred as
  "blocked / never entered" and is actually `USER_ENDED`.
- **Five diagnostic stats models** (`bbrun`, `bbswitch`, `bbnav`, `bbpanic`,
  `mssnNavStats`) and thirteen missing fields in four existing ones.
- **`DockCapabilities.fr`** — a dock could report it was refilling while the
  capability model denied it could refill at all.
- **`legacy_map_keys` wrote only half its pair**; `user_pmapv_id` was missing,
  though certain devices require it.
- **Map-edit V3 is nine operations, not one.** Two of them have no V1 or V2
  equivalent, so thresholds moved rather than vanished.
- **`verify-writes`** described `pwReturn` as a boolean — it carries two ranges
  in one field, and the wrong hint led a tester to report a correct value as
  stale. It also reported dotted setting keys as absent on every robot;
  `audio.volume` is a write address, not a read key.

## Upgrading

```
pip install --upgrade "roombapy-prime@git+https://github.com/johnnyh1975/roombapy-prime.git@v0.3.0b4"
```

Roomba+ v4.0.0a33 pins this version. If you run the integration, upgrade both.
