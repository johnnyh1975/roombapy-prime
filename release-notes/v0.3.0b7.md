# roombapy-prime 0.3.0b7

Required by Roomba+ **v4.0.0a37**.

**Favourite buttons could not run their favourite.** Four causes, all on the
same path, all in this library.

## Why pressing a favourite did nothing

@chairstacker's favourite buttons appear and disappear correctly since a36.
Pressing one did nothing at all, and the reason was a single missing field.

The one region command **confirmed working on real hardware** carries
`initiator: "rmtApp"`. A favourite's stored command def carries an initiator
too — and `_favorite_from_json` read eleven of its fields and not that one, so
`to_json()` omitted the key entirely.

Comparing the two payloads side by side, that was the **only** difference.

Not proof: a PUBACK with no effect has had several causes here. But sending a
field the server stored, in a payload otherwise identical to one that works, is
the change to make before looking further.

## Three ways the same path could crash

Found by feeding malformed command defs through the parser, not by a report.

**A command def with no `command` key.** The parser reads commands tolerantly —
an unknown command becomes `None` rather than dropping the favourite. Then
`to_json()` raised `AttributeError` on that same `None`. So a favourite that
survived parsing died the moment somebody pressed its button.

**A command carrying a string the enum does not model.** Same crash, different
route. It is sent as it came now: the server stored it, and this library does
not invent a replacement.

**A command def that is a string but not valid JSON.** `json.loads` raised
straight out of the parser, and the caller catches per favourite — so one
malformed command def **deleted a working favourite from the user's list**.
Now the bad def is skipped and the favourite survives.

> Tolerant on the way in and strict on the way out is not tolerance.

## The tools now say when they are older than the library

`roombapy-prime` and `roombapy-prime-tools` are two distributions. Upgrading
the library leaves the tools where they were, and nothing said so.

@chairstacker installed b6, ran `verify-writes custom_initiator`, and was asked
to check the cleaning history — an instruction b6 had removed, because `find`
creates no history entry. He reported the missing entry as a result. The tool
was still b5.

**Upgrade the tools, not the library** — they pull the matching library with
them:

```bash
pip install --upgrade "roombapy-prime-tools@git+https://github.com/johnnyh1975/roombapy-prime.git@v0.3.0b7#subdirectory=tools"
```

`verify-writes` now says so at startup when the two disagree, and names that
command. A warning rather than a refusal: an older tool against a newer core
usually works, and stopping someone mid-field-test over a version string would
be worse than the confusion it prevents.

## `pwReturn`'s upper three, described correctly

The tool still called 100/101/102 "Standard / Medium / High". That labelling
was invented here, and it cost a tester a retraction of a correct observation.

iRobot calls them `mission`, `refill` and `refillAndRoom`, and the app's own
subtitles say they are **cumulative**:

```
100  before and after cleaning routines
101  ALSO during refills
102  ALSO in between rooms
```

Captured from @chairstacker's screenshots and confirmed in both directions — he
wrote 100 from Home Assistant and his app showed "Standard".

## Smaller

- **`FloorPlanFeatureProperties.type` has a vocabulary.**
  `P2MapFloorPlanSegmentType` declares `interior`, `exterior`, `door` and
  `unknown`, so a segment says whether it is a wall or a doorway. Recorded on
  the class rather than typed — no capture shows whether the names or the
  integers arrive, and a renderer currently draws all three the same.
- **A new `initiator_mission` check.** Marked risky, and **nobody is asked to
  run it**: only a real mission produces the app-timeline entry that would
  answer whether a custom initiator survives, and the answer changes nothing —
  this integration's own sensor already labels `localApp` as "Home Assistant".
  It exists so somebody curious about their own timeline does not have to build
  it.
- **The vendor gap report ignores framework internals.** Every remaining
  "unreviewed" enum turned out to begin with an underscore — Flutter widget
  states swept up by the extractor, producing a count that never went down.
  Vendor enums and classes both report **zero unreviewed** now.

## Upgrading

```bash
pip install --upgrade "roombapy-prime-tools@git+https://github.com/johnnyh1975/roombapy-prime.git@v0.3.0b7#subdirectory=tools"
```

Roomba+ v4.0.0a37 pins this version. If you run the integration, upgrade both —
tag b7 first.
