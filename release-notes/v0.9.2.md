# roombapy-prime 0.9.2

**A robot can tell its caller that its topic prefix changed.**

A Prime robot sends and receives its commands under a topic prefix that
belongs to its iRobot deployment, read at login. If iRobot moved a robot
to another deployment while a session runs, the robot would keep using
the old prefix until it is built again, and its commands could be
acknowledged and ignored. Such a move has not been seen in the field; the
one mismatch known so far was already there at login, and 0.8.3 handles
that when the robot is built.

0.9.2 watches for it (#101, @Rickeeh). On every successful login, the
library compares the prefix a rebuild would use with the one the robot
was built with. When they differ:

- `robot.topic_prefix_changed` turns true and stays true for that
  instance;
- a warning is logged once, with the robot id masked;
- the observer set with `robot.set_topic_prefix_changed_callback()` is
  called. It runs on the event loop, possibly during renewal, so it
  should schedule the rebuild rather than do it.

The library changes nothing else: renewal, subscriptions and command
sending are as in 0.9.1, and no new lock or wait is added. A caller that
ignores the signal behaves as before.

A robot built from its own deployment's prefix is **not** signalled when
a renewed login lists no prefix for that deployment and only the
account's: that is incomplete discovery, and a rebuild would swap a
known prefix for a guess.

## Tested

- The library's suite passes on Python 3.13 and 3.14 (1,543 tests); ruff,
  strict mypy and the per-module coverage floors pass.
- A table of nine cases built through `CloudAccount` and the factory
  checks that the signal follows the prefix a rebuild resolves, and that
  an identical next login does not signal again. Twelve targeted
  mutations of the new code each fail at least one test.
- Detection was tested with synthetic logins only, not against a real
  deployment move.
