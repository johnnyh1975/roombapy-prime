# v0.1.11a31

**The virtual-wall HTTP 500 is solved.** `virwall` starts with a count of the walls, and we were
never sending it.

## The finding

```json
"params": {
  "virwall": [
    2,                          ← the number of walls, as an integer
    ["1", 1, 9.8134, 2.3, ...],
    ["2", 6, 0.4194, -4.6, ...]
  ]
}
```

Confirmed from the app's own `CommandSerializer` bytecode: it builds one JSON array, adds
`walls.size()` as the first element, and only then appends the walls.

Three things make it certain rather than plausible:

- It is the **only** `.size()` call in the entire serializer — all nine commands, over a thousand
  lines.
- `adjust_furniture` is equally list-based and has **no** counter. This is a quirk of one command,
  not a convention.
- The bytecode shows the count going into the same `JsonArrayBuilder` the walls go into.

## Why it produced 500 and not 400

The body was valid JSON, so parsing succeeded. Deserialisation then read position 0 expecting a
number and found an array. A structurally malformed body would have been rejected earlier, with a
400.

That 500-not-400 detail was noted repeatedly in this investigation and read as evidence of a *type*
problem inside a wall. It was evidence of an *extra element* before the walls.

## Why no amount of field testing found it

Three testers between them ruled out wall count, zone type mixing, map count, account, map
version, our own filtering, the request envelope and all three `response_type` variants.

None of it mattered: the payload failed at element zero, before any of those reached the
deserialiser. What their runs did achieve was narrowing the question enough to be worth asking of
the APK — which is how the count was finally found, in an unfiltered raw dump after several
filtered passes had missed the four relevant lines.

## Consequences worth knowing

**A partial list is now doubly destructive.** All three zone kinds share one array, so sending only
the wall you want to add already deleted the rest; now it also sends a count that matches the
partial list. `--only-first-wall` still exists but the question it was built for is answered, and it
should not be used casually.

**`response_type` is untested again.** All three variants were rejected before the count was known
— so they were rejected *for the count* and say nothing about `response_type`. The tool still tries
all three, now for the first time meaningfully.

## Also in this release

- **Type-variant probing removed unused.** Built to guess whether the wall id should be an integer;
  bytecode then settled it directly (id is a String, type code an Int). Sending known-wrong
  variants would have spent real writes on real maps.
- `--only-first-wall` actually truncates the payload now. It previously announced "sending 1 of 2"
  and sent both, because the command was built before the list was trimmed — a tester spent a
  session on a test that never ran.
- `take(4)`: the app takes exactly the first four polygon points. This library dropped a closing
  point only when the ring was closed — identical for rectangles, wrong for anything else.

881 tests passing, ruff clean.
