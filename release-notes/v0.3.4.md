# roombapy-prime 0.3.4

Two traps in the schedule endpoints, both found in the field by @Nguyen
running a custom stack against this library directly -- no Home
Assistant, a Combo on the cloud path.

Neither is a bug in this library, and that is what makes them worth
writing down: **the API accepts what you send and the result is wrong
rather than refused.** Nothing at the call site suggests otherwise, so
the knowledge has to live somewhere.

## `create_schedules()` takes a list and keeps one

The signature is `list[ScheduleOptions]` and the body is a JSON array,
so it reads as a batch create. Send two and the server answers **HTTP
200** and stores only the **last** one. @Nguyen sent "Sat/Sun deep
clean" and "Wed spot vacuum" together; `get_schedules()` came back with
a single household_schedule_id holding only the second. One call per
schedule created both correctly.

A warning is now logged when the list holds more than one. Not an
exception: the endpoint does accept the request, and raising would break
a caller passing a one-item list built elsewhere. But a 200 that drops
data should not pass unremarked.

## `delete_schedule()` wants the outer id

A create response carries two id-shaped fields for the same schedule,
and the second is the first plus a robot suffix:

```
household_schedule_id       hh_irbt.hh.<uuid>_<token>_s
schedules[0].schedule_id    hh_irbt.hh.<uuid>_<token>_s_K452
```

The nested one returns **HTTP 500**. Confirmed either way with
`get_schedules()` before and after.

A 500 rather than a 404 is what makes this expensive: it reads as a
server fault rather than a wrong argument. Both forms are now in the
docstring, with which one the parameter wants.

---

Days round-tripped exactly as sent in the same session, ISO 1=Mon..7=Sun
confirmed on that account — so `create_schedules()` and
`get_schedules()` are now end-to-end field-confirmed on the cloud path,
which they had not been.
