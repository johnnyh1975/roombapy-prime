# roombapy-prime 0.3.0b17

Three releases have now reported on a zone-name search that had not
happened. This one is about the tests that let that keep occurring.

## The call never reached the parser

`parse_map_bundle` is a module function; the tool called it as a robot
method. `PrimeRobot` has no such attribute, so it raised — and b16's
dict-link fix is what made the line reachable at all, so the error
appeared one release after it was introduced. @utkjmitch and
@chairstacker both hit it immediately.

## The tests agreed with the broken call

Every bundle test mocked `parse_map_bundle` **as a robot method**. The
mocks matched a call site that could only ever raise, so two bugs
shipped green behind them.

b15's own notes named this exact failure mode for the `zone_layers`
fixture, one function down. Nobody looked one function up.

Tests now build a real tar.gz and feed it through the real parser.
Fourteen failed when they were switched over.

## Absence and failure are different findings

`_zone_names_from_bundle` returned `{}` whether the read failed or
found nothing, so the caller printed "no zone names found" after a read
that threw. It returns `None` on failure now, and the caller says the
question is unanswered by that run.

@utkjmitch: the same sentence b15 fixed, one level up.

## The blid leaked through a composite id

Diagnostics redacted every credential-shaped field and then carried the
blid in clear text inside `map_id`, which is `<blid>-<epoch>`.

Substring redaction already existed — built after an earlier report
about `p2map_id`, with a docstring saying that redacting the field
called `blid` while leaving copies elsewhere is worse than not claiming
to redact at all. It had been wired into one section. It now covers the
whole payload.
