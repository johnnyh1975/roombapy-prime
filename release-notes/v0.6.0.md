# roombapy-prime 0.6.0

Up to date with the Prime app 3.2.0 (build 3020012): its error texts, its
model table, its new settings and capabilities, and the part reset as the
app sends it.

## Breaking: `reset_robot_parts()` needs part ids

```python
await robot.reset_robot_parts(["35"])               # part 35 is new
await robot.reset_robot_parts(["35", "36"], {"36": 0})
```

`part_ids` is required on `PrimeRobot` and `PrimeRestClient`. An empty list
or an empty id raises `ValueError`. Without ids, 0.5.0 sent a body that
named no part.

## The part reset sends the app's body

```
POST /v1/robots/{blid}/parts
{"parts": [{"part_id": "35", "counter": 0}]}
```

This is the request both app 3.0.0 and 3.2.0 send. 0.5.0 added `robot_id`
and `num_parts`, which belong to the response. It is also the body Classic
robots are confirmed to accept through `set_robot_part_counter()`; the Prime
client keeps `json.dumps()` spacing. It has not been sent to a Prime robot
yet.

## Five Prime models were not recognised

`is_prime_sku()` and `sku_generation()` now know `Q4` (Roomba 115 Vac), `Q5`
(125 Vac), `F2` (Mini 2), `W3` (725 Combo) and `Z2` (925). The last two are
new in 3.2.0; the first three were in 3.0.0 and missing here. Robots of
those models came back as `"unknown"`.

The app's full table is in the library now:

```python
from roombapy_prime.auth import prime_product_mode

prime_product_mode("W355020")
# PrimeProductMode(mode='robot_725_combo', sku_prefix='W3',
#                  model_name='Roomba® 725 Series Robot',
#                  product_name='Roomba® ProClean Max 725')
```

If a model in the table is missing from the generation check, the import
fails.

## Parts catalogue

```python
catalog = await rest.get_parts_catalog("R980020", "de-DE", "DE")
for part in (await rest.get_robot_parts(blid)).parts:
    entry = catalog.part(part.part_id)
    print(part.part_id, part.counter, entry and entry.guide_url)
```

The catalogue lists, per model, each part's name, replacement part numbers,
interval keys, care guide (`guide_url`) and shop link (`buy_url`). It is an
unsigned request to the content host, as the app makes it, and works on
both REST clients. Part ids are numbered per model, so fetch it with the
robot's own SKU.

## What app 3.2.0 added

- **Settings:** `sprayMode` (AI stain detection: ignore, avoid, clean),
  `dryDMode` (AI dirt detection: normal or boost), `sanitizationMode`
  (sanitising tablet). On `RobotSettings` as `spray_mode`,
  `dry_debris_mode` and `sanitization_mode`, with `SprayMode`,
  `DryDebrisMode` and `SanitizationMode`. Write them with `set_setting()`.
- **Capabilities:** `CapabilityFlags.seal_force`, `water_spray`,
  `dry_debris_mode`, `sanitize`, `default_capabilities`, and
  `DigiCap.sanitize_tabs`.
- **Mission parameters:** `CommandParams.seal_force` and `spray` (0/1),
  for whole missions and regions. SealForce is set per cleaning, not as a
  setting.
- **Dock wash level 4**, `DockPadWashing.DEEP_HOT_WATER_WASH`. For `pwHeat`
  it behaves like level 3: noHeat, defaultHeat and highHeat.
- **`MapVerifyResult.OVERLAP` (3).**
- **Doorway thresholds:** `PolicyZoneFeatureProperties.threshold_status`
  maps `threshold_type` onto the app's five statuses (`ThresholdStatus`).
- **`Initiator.GOOGLE`.**

None of these has been seen on a robot yet. They are read under the keys
the app uses.

## Error texts from 3.2.0

The same 112 codes in all eight languages. 173 of the 1,792 strings
changed, in 79 codes, and most read better: Portuguese and Dutch are
cleaner and consistent, a truncated French text is complete, and the
English 251 no longer shows a raw `%robotName`. The table is now generated
by `scripts/generate_vendor_errors.py`.

Where 3.2.0 made a text worse, `vendor_error()` gives our own instead:

| Code | 3.2.0 | Now |
|---|---|---|
| 234, all languages | "You can currently perform a sweeping task" — what to do is gone | "Attach the mop to mop the floor. You can still vacuum without it." |
| 4003/4004 | English says the dock's software is updating, the other seven still say the robot | all eight say the dock; English "Dock software is updating" |
| 18/1010, English | the title lost "put it on the dock to charge" | the explanation starts with it |
| French codes | "(1 008)", "(4 003)" | "(1008)", "(4003)" |

`vendor_error(code, language, as_shipped=True)` returns iRobot's text
unchanged. Broken placeholders (`%robotName`, `@val` run into the next
word) are repaired on the way out, as ha_roomba_plus did on its own copy
of the table, which it drops in 4.3.4 for this one.

## The vendor reference is app 3.2.0's

`vendor_reference.json` was regenerated over the same scope as before. The
regeneration found the new dock level, the new map-verify value, the
resolved Google initiator and two values that were wrong in the 3.0.0 file.
`IrobotRegionType` is gone from the app, so `enum_values("IrobotRegionType")`
now raises. The value-set check passes again; it had failed since 0.5.0
without anyone noticing, and it now runs in CI.

## For ha_roomba_plus

`sku_generation()` now returns `"prime"` for the five models above. The
integration does not call `reset_robot_parts()`, so the breaking change does
not touch it. `set_robot_part_counter()` is unchanged.
