# roombapy-prime 0.3.0b8

**One report, three fixes.** @ratpic83 ran INFO logging for days waiting
for a mid-mission MQTT drop to eat a mission-end transition. One landed,
the transition survived — and the log that proved it also showed where
the drops come from.

## The 55-minute clock was us

Twenty-six disconnections in one day, each exactly 55 minutes after the
last. No gaps, no clustering, identical while the robot was docked,
cleaning, and idle overnight.

The ordering was the finding:

```
15:21:30.521  authenticated, 1 robot(s) found
15:21:30.524  reconnecting (4 persistent subscription(s) to restore)
15:21:31.491  MQTT connection dropped (Normal disconnection)   ← reported here
15:21:31.492  reconnecting (4 persistent subscription(s) to restore)
15:21:32.457  MQTT reconnected, watch resumed
```

Authenticate, reconnect, *then* the drop. `Normal disconnection` is
paho's phrase for a clean client-initiated close — ours, from the
proactive token refresh disconnecting the old connection before opening
the new one.

So the watcher was warning about an event it had scheduled itself, and
then starting a **second** reconnect racing the one already in progress.

**Two earlier attempts guessed at this and both were wrong.** b2 rotated
the `client_id` on the eviction theory; b3 reverted it because a
self-chosen id does not connect at all. The code then settled on "the
phone app and this library evict each other", which is why
force-quitting the app on every phone changed nothing for anyone whose
drops arrive on a fixed interval.

A deliberate disconnect is now marked as one. **You should see the
55-minute entries disappear entirely**, not move to a quieter level — a
scheduled refresh that works as designed is not news.

## `watch resumed` now means acknowledged

Twice in the same day, one millisecond apart:

```
23:36:35.106  no SUBACK within 3.0s for ['v011-irbthbu/th…']
23:36:35.107  MQTT reconnected, watch resumed for $aws/things/<THING>/…
```

The second line claimed success for a subscription the first line said
was never acknowledged. An unacknowledged subscription delivers nothing
and looks exactly like a robot with nothing to say — **which is the
mechanism by which a mission-end transition goes missing**, the failure
@ratpic83 had been watching for.

Unacknowledged subscriptions are now named, counted and retried with
backoff instead of being announced as a working watch.

## A refresh timeout is not an error

```
16:16:41.624  WARN   MQTT reconnect attempt failed (Connect timed out)
16:16:41.629  ERROR  proactive token refresh failed for <THING>
16:16:43.591  WARN   MQTT reconnected, watch resumed
```

Self-healing in about two seconds, logged at ERROR with a full
traceback, a dozen times a day. The retry is the design — the refresh
runs five minutes before expiry precisely so a failed attempt has room.

Timeouts now get a warning with no traceback. A real failure — auth
rejected, malformed token — still gets the full stack, because there the
stack is what identifies it.

## The validation report now shows `digiCap`

@ricrog1135's `W155020` run reported `digiCap` in `state.reported` —
and the report printed only that the key exists, not its contents.

Nine capability gates are modelled from iRobot's own table and **not
one has ever been observed on a real robot**. That has been the
standing ask in every status update since July, and the run that
finally carried the answer did not show it.

`roombapy-prime-validate` prints the dict now. It holds integers and no
identifiers.

## A late SUBACK is still a SUBACK

Corroboration from @utkjmitch's household caught a problem in the fix
above before it shipped. His instance logs `no SUBACK within 3.0s` on
**every** reconnect, not twice a day — and the retry introduced here
would have turned that into a reconnect loop every 55 minutes, for
subscriptions that were most likely acknowledged a moment later.

`last_subscribe_unconfirmed` records which subscriptions were missing
when a three-second wait expired; paho keeps filling the confirmed set
from its own thread afterwards. The watcher now re-checks a second
later, and acts only on what is still missing.

His report also settled the mechanism without needing the interval at
all: ten seconds after a drop, `replace_token` reports on the same
connection. The drop and the refresh are one event, not two on the same
cadence. And his robot was dead throughout — flat battery, off its dock
— while the 55-minute cycle ran anyway, which puts the whole thing
between the integration and the broker with nothing robot-side
involved.

## Documentation

The README described virtual wall writes as broken with an unsolved
HTTP 500 in three places. That was solved before 0.2.0b1 — `virwall`
starts with a COUNT of the walls — and the sections were never revised.
@utkjmitch found the contradiction while planning a field test and
asked rather than running it.

What is actually open: every confirmed write **resent its zones
unchanged**. A write carrying a modified list has never been attempted,
and `set_virtual_wall` replaces the whole shared list.

## `models` exports its names explicitly

`models/__init__.py` re-exported `TimeEstimate` and `TimeEstimates` on a
plain import line. Every other module in that package arrives through a
star import and carries its own `__all__`; these two did not.

For a `py.typed` package that matters: under `mypy --strict`, a consumer
importing them gets *"does not explicitly export attribute
TimeEstimates"*. It cost ha_roomba_plus a red CI run on three call
sites — and was invisible while developing, because an editable install
lets mypy read the working tree rather than the built package.
