# roombapy-prime 0.2.0b14

Required by Roomba+ **v4.0.0a28**.

Six field checks were run in one evening (@DaRealGuGu), and between them they answered every
outstanding question about this library — including one the model had answered wrongly.

## The time-estimates model was built against the wrong response

`POST /v1/time-estimates` had never been called by anyone. The model came from the app's **simulator**
response, and the real one uses different names throughout:

```
modelled   pmaps / pmap_id / regions / time_estimates / estimate / minute
actual     smart_maps / smart_map_id / areas / estimates / value / seconds
```

**The parser read a real response as zero estimates.** Anything built on it would have stayed silently
empty, which is the same output as a robot with nothing to say.

Three details that would each have been wrong on their own:

- the unit is **seconds**, not minutes — off by sixty and still plausible on a progress bar
- there is **no `confidence` field**; `deviation` sits where one was expected and reads 0.0 on every
  estimate. Nothing is filtered on it, because filtering on a field that is always zero would discard
  everything the day it stops being zero
- there is **no whole-mission total**. A caller wanting a duration has to sum the areas it plans to
  clean, which is the honest arithmetic anyway

The simulator's names are kept as a fallback branch, at the cost of one loop.

## The orientation check changed what it said it would not

`set_map_orientation`'s abort notice promises it "resends what is already there". It sent the argument
default of `0.0` regardless, and a tester's map went from `-0.0035` rad to `0.0`.

Invisible on screen, and still a change made by a check that said it made none. **A tool that
misdescribes itself is worse than one that refuses** — the point of these checks is that a tester can
trust the summary before running them.

Without `--orientation` it now reads the map's current value and sends that back.

## The clean-score model had four fields only at runtime

`CleanScoreRegion.from_json` already read `high_traffic_enum`,
`mission_last_cleaned`, `mission_last_unfinished` and `smart_clean_prefs`; the dataclass did not
declare them. They worked and appeared in no type — the kind of gap that survives until somebody
reads the class instead of the parser.

**Higher means dirtier**, settled by an eleven-room account (@jouwdan) after a four-room one had
looked ambiguous:

```
mission 33 (just now)   0.0, 0.0, 0.0   last_updated_by: batch_decay_skipped
mission 32              0.15, 0.1744, 0.1744
mission 27              0.2801, 0.4
mission 25              0.4201
mission 12 (long ago)   0.6973
```

The rooms cleaned by the newest mission read exactly zero, with decay skipped because they had just
been reset. The room untouched since mission 12 is approaching `clean_score_ranges: [0.7]`, which
makes that threshold "needs cleaning" rather than "clean enough".

The four-room account looked ambiguous because two of its rooms shared a mission and differed
anyway — room size and traffic move the rate, not the direction.

So anything built on this is **dirtiness**. The field name points the other way, and an automation
written from the name alone would do the opposite of what its author meant.

`mission_last_unfinished` needs no interpretation and may be the more useful half: it answers which
room did not get finished.

## The settings check could never have succeeded

`settings_roundtrip` is the check six controls are waiting on -- a volume slider for every Prime
robot, the charge light ring, mop dry duration, pad wash frequency and two evacuation settings. It
read the settings shadow off a `state` attribute.

**`ShadowResponse` has no `state` attribute.** Its fields are `topic` and `payload`. The lookup fell
through to the object itself, found no `reported` block in it, and reported:

```
could not read rw-settings -- this robot may be EPHEMERAL tier
```

Which is the worst kind of wrong: it reads as a fact about the tester's hardware. His robot reports
`rw-settings` perfectly well and his own diagnostics list it among the seeded shadows.

So the check has been unable to succeed since it was written, while being recommended repeatedly as
the one run that unblocks the most. Four shapes are now handled and each is pinned by a test.

## The tool died on its own tick mark

The status lines print U+2713. A cp1252 console cannot encode it, so `print()` raised
`UnicodeEncodeError` **before any check did any work** — and the error named an encoding rather than
anything the tester had done (@utkjmitch, Windows).

`PYTHONUTF8=1` fixes it from outside. Nobody should have to know that. `errors="replace"` is now set
on stdout and stderr as the first statement of `main()`, which costs a mangled tick mark on a console
that could not have displayed it anyway.

## Confirmed by the same run

- **Mission history is a bare array** — 62 of 62 entries parsed from a real robot, not only from the
  vendor's own sample
- **`set_map_name` and `order_favorite` both take**, with the rename verified in the iRobot app
- **`automations` returns `[]`** — the endpoint is alive and that account simply has none, which is a
  better answer than the "probably dead" it replaced

1,075 tests passing.
